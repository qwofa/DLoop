# DLoop 3.6.1：需求确认与最终验收的场景化展示

基于已合入并冻结的 `v3.6.0`，发行状态为 `frozen`，由 `v3.6.1` 标签固定。本次修正人类入口的展示粒度与填写引导，按用户指定的补丁版本 3.6.1 交付。六阶段、档案格式、批准、候选与 Unity 采集合同保持原有职责；不修改 README 中的稳定设计意图。

## 人看到什么

需求入口先给出当前问题、期望变化和待决定事项，再按可以独立判断的业务场景组织正式需求。最终验收沿同一场景展示真实结果、体验入口和偏差。影响批准的范围、代价、风险、非目标与未验证部分直接可见，过程材料按需追溯。

一个场景可以跨多个界面，一个界面也可以承载多个场景。结果可分别接受或退回、关键边界无法在当前展示中看见，或初始条件与入口显著不同时，才考虑拆分。展示场景与实施切片不要求一一对应，不用控件、Prefab 和视觉状态数量决定粒度。

| 当前要判断什么 | 优先使用什么 |
|---|---|
| 入口和信息是否清楚 | 已有截图及必要标注 |
| 操作衔接是否合理 | 简短分镜 |
| 布局、尺寸或遮挡 | 必要时在 Unity 预览 |
| 手感与时序 | 必要时提供 Unity 最小可体验内容 |
| 规则与数据结果 | 具体输入及结果示例 |

材料够用即止，不统一套前端模板，不强制原型或媒体数量。现状、设计示意、待实现原型与最终运行证据明确区分；暂不可体验时暴露缺项。

## 示例：批量处理条目

以下是虚构业务示例，用来说明展示粒度，不是已实现功能或测试通过声明。真实交付中的资产、入口与证据必须来自项目。

需求入口可以直接写成：

> **批量处理条目**
>
> 用户现在需要逐件操作；本次希望多选后一次确认，移除所选条目并汇总获得材料。
>
> 受保护条目不能被分解；取消后条目和材料不变。本次不做自动筛选。
>
> 沿用已定位的条目格、按钮和确认弹窗表现，交互依据在对应项目材料中引用；依据尚未核实时明确待核实。
>
> **需要决定：稀有条目是否允许批量分解。**

选择与确认的衔接不清楚时补分镜；已有截图已经说明入口时不再做可点击原型。按钮按下变暗、松开回弹不单列场景。若本次需求就是改变长按确认时机，则应展示有关时序、触发与取消边界。

最终验收仍使用“批量处理条目”，链接已批准需求，给出真实场景或菜单入口、包含普通与受保护条目的初始配置，以及多选、取消、确认后的实际结果和证据。数据保护与重复触发等可重复检查附测试结果，操作是否顺手留给人判断；缺少实际运行结果时明确未验证，不用规划截图代替。

## 实际改动位置

- 新建档案的人工导航直接指向需求和验证总览；两份总览提供可删除的填写提示，保持空白业务事实，不预建场景清单或状态矩阵。
- 需求与验收规则通过原有动作路由投递；实施规则沿用需求场景名称，最终结果链接需求正文，不创建第二份规格或批准状态。
- 实施与最终验收角色的现有输出、操作边界直接包含必要的场景要求；交接准备与下游独立读取返回同一要求，不依赖协调者转写或下游读取常驻入口。返修沿用实施角色要求。
- 冷读围绕当前业务决定检查理解断点，不以 AI 能读懂推定人已理解；遇到断点不机械增加篇幅和控件状态。
- dloop-ui 的真实 Prefab 截图仍只证明可见现状，规划附件仍供实施使用；按业务结果组织人的展示，不将每个标注条目变成独立验收场景。

## 验证与边界

验证新建档案、正文修改与确认、场景引用、候选和最终批准、只读分享，以及当前版本安装与卸载。保留现有门禁，不新增标题、字段或媒体数量校验。Unity 采集代码未修改；实际人类理解速度和 Unity 试玩效果需要后续真实交付观察，不用规则检查或自动测试冒充。
