# 第 3、4、6 项待评估改动计划

状态：第 3、6 项仅供用户评估，尚未实现；第 4 项按用户反馈不推进。不属于 3.6.3 已授权实现范围。批准后依据最终公开合同和格式变化单独确定目标版本。以下保持单线实施，不增加常规人工确认点，也不处理人工改写受管状态、跨版本作业或外部破坏。

## 第 3 项：既定业务目标下，允许窄范围补充写入范围

### 推荐决定

允许协调者在既定业务目标下追加必要文件或目录，保留当前成果；不建设任意修改契约的通用入口。先改善实施前调用链调查；追加能力用于仍会在实施中暴露的真实遗漏。

### 正常场景与预期结果

例如已批准实现批量操作，实施时发现还需要调整同一责任域内的一处调用接线或直接回归测试，但该文件未列入任务包。实施者在修改该文件前返回遗漏、理由和必要路径。协调者确认业务目标、验收、公共接口、跨模块数据责任及安全回退均不变后追加范围。原身份、已完成代码和修改占用保留，实施者取得新版本任务包继续工作。

### 最小流程

1. 只接受处于活动实施状态的切片，包括已经正式启动的返修；候选待评审、已经接受或熔断状态不直接扩围。初次发现遗漏时先交还协调者判断，避免先熔断再尝试补充。真正越过业务合同仍立即熔断。
2. 由协调者提交当前执行身份、当前契约版本、需要追加的路径及原因；保留原范围，不接受目标、验收、依赖、公共数据责任、不变量或回退合同的顺带修改。
3. 在现有事务锁内核对身份、批准与工作区。旧授权范围外若已经出现本轮修改，继续按原越界流程阻断；追加范围不能追认此前越界写入。
4. 在扩大授权前保存新增路径的当前基线。与原基线合并时保留原有文件的执行前内容，重叠路径只保留原记录，绝不把已完成修改保存为新的回退起点。已有 SVN 全局基线继续保留。
5. 原子更新任务包范围、契约版本及历史、修改占用范围和合并基线；失败恢复到调用前状态。旧检查点因契约变化失效，原评审快照和批准方案历史不改写。
6. 协调者沿现有验证补充能力增加必要验证。实施者重新读取当前合同，完成新范围，形成覆盖现契约的最终检查点，再走原候选和独立评审。

### 不处理的情况

需要扩大业务目标、改变验收、修改公共协议、跨模块状态归属、存量数据规则或安全回退时，仍重新设计和划分切片。范围补充不是用户业务批准，也不放宽已批准的高风险操作边界。内部整理可以自主决定，不意味着可以自行扩围。

### 成本、风险和验收

改动涉及范围补充入口、任务包版本历史、基线合并、原子状态提交、角色材料和回归验证；成本中等，主要难点是继续使用正确的回退起点。

必要验收：新增文件和既有文件扩围；目录与文件重叠；重复请求；陈旧契约请求拒绝；旧检查点失效；追加失败不改变成果与状态；扩围后中断仍恢复到对应文件的正确基线；返修保留原候选与问题集；真实业务边界变化仍停止。

若需要先低成本改善，只补实施前调用链与写入范围核对即可，但这不能完全消除实施中发现遗漏后的回退成本。

## 第 4 项：不推进

用户认为当前没有必要，保持现有恢复内容保存方式。本次不安排大资源专项测量，不拆分恢复文件，也不改变持久格式。此前的拆分建议不作为后续待办。

## 第 6 项：验证范围和真实宿主环境分别判断

### 推荐决定

按实际影响决定测试范围，真实宿主验证作为必须完成的具体验证项目。保留现有三个验证等级和任务包结构，不新增“环境等级”、测试调度器或第二套验证状态。

### 登录后的游戏协议场景：建议以真实操作验收为主

用户说明游戏操作依赖登录后的游戏内协议，单独编写程序测试的准备成本较高。第 6 项方案因此需要把“验证正确性”和“必须编写自动化脚本”分开：

- 使用现有测试账号和真实客户端登录，按本次功能的少量关键场景实际操作；不为每个功能重建登录、账号状态和协议驱动脚本。
- AI 先核对发起请求、响应处理、数据更新和界面刷新之间的真实调用链，整理可执行步骤和可观察结果。代码检查不能单独记为游戏集成通过。
- 实际操作同时核对界面、业务数据和已有请求/响应日志。日志不足时仅在本次关键位置补少量开发日志，不建设通用采集平台。截图只证明当时可见表现，不证明服务端持久状态正确。
- 对资源扣除、奖励发放等相关功能，核对操作前后数量，并在需要时重新进入界面或重新登录复查；有现成服务端查询或日志时优先使用。重登检查不能替代所有持久化与并发验证。
- 根据本次风险选择成功、取消、条件不满足、重复点击、返回关闭、断线重连等相关分支，不把所有分支机械用于每个功能。难以重现的关键服务端失败必须明确未验证，必要时与服务端联调，不能用无报错替代通过。
- 不依赖登录且容易独立验证的本地计算、过滤、排序、数量边界，可以保留少量程序测试；不为测试强行重构整条网络流程。高频稳定场景有明确重复成本后才考虑自动化。

人工操作可以形成正式验证证据：使用的构建与环境、必要初始条件、实际步骤、期望与实际结果、关键数据或日志定位。由实际操作者提供结果，AI 整理记录与分析；不能在用户尚未执行时推定通过。计划时把这种真实操作登记为验证方法，不在交付末尾擅自豁免已经约定的测试。

这一节仍是待评估方案，没有修改当前验证策略或机器提交条件。

### 最小策略

| 变化 | 测试范围 | 必要的宿主验证 |
| --- | --- | --- |
| 边界明确的局部 UI 接线、局部行为 | 定向验证，覆盖直接变化、相关调用边界和稳定回归 | 在真实 Unity 场景验证接线、输入、遮挡和状态清理等本次相关影响 |
| 共享核心、公共协议、持久状态或跨模块基础能力 | 受影响责任域完整验证；影响无法界定时升级项目全量 | 覆盖真实消费者和集成入口 |
| 正式发布、影响无法界定、发现跨模块回归或集成后无法归因 | 项目定义的完整发布前集合 | 当前最终工作区的真实集成验收 |

具体所需的真实宿主检查写入现有验证集合，等级与理由继续由唯一策略形成。“用真实 Unity 执行”本身不再自动扩大到全部无关模块；也不能因采用定向等级而省略真实集成检查。

### 阶段流转

计划阶段记录影响范围、验证等级、理由和具体验证集合。实施、返修沿用该判断；出现新影响或失败证据时，通过已有补充入口升级。每个候选仍须通过当前登记验证。最后一个实际修改完成后，按最终风险补足集成验证；正式发布前运行项目完整集合。

候选、工作区和风险未变化时复用有效结果，不因最终验收或冻结名称重复执行。宿主环境不可用时明确未验证，并保留相应提交阻断；不能把本应运行的验证降级为文字确认。正式安装和发布的专项授权不变。

### 改动与验收

主要调整唯一验证策略、对应说明和行为评测，原则上无需改变运行时格式或机器门禁，成本低于第 3、4 项。

验收用四类实际任务检查策略选择：局部 Unity 接线、共享 UI 基础能力、范围未知的集成失败、正式发布。分别确认验证范围恰当、真实宿主检查未被省略、新风险能升级，以及后续没有新变化时可以复用。规则文字通过不算真实验证已通过。

## 建议评估顺序

优先评估第 6 项的真实游戏操作验收方案。第 3 项继续讨论范围遗漏发生时是否值得保留成果扩围；不做它仍可沿既有路径恢复作业。第 4 项不推进。
