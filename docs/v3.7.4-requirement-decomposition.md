## 交付范围

沿用 3.7.3 已有的业务场景、计划覆盖、切片契约和最终集成验收，补足拆分粒度、共同依赖决策、临近实施细化及调整后的检查。局部修改仍按普通任务处理；正式切片对应可分别验收的结果，不按文件数、技术层或编码步骤分割。

计划正文关联需求场景、切片结果、前置依赖及验收依据；已有正文足够时不增加表格。共同接口、数据归属和执行顺序在设计中决定一次，各切片引用，不复制契约。协调者做覆盖、边界、顺序和交接价值的语义自检；不新增计划评审角色或用户批准。

预制体缺失按当前流程处理：先查找相关资产，缺位置或业务事实才集中询问；已授权制作时在现有设计和实施范围记录建议，规划阶段不创建资产。未匹配的目标继续保留需求和缺项去向，不创建计划新增模型或恢复旧版声明命令。

## 复杂度与影响

- 业务规则修改集中于需求、计划、执行、最终评审和 DloopUI 入口。
- 沿用用户既有的正常工作流审查边界；开发前核对目录与版本，稳定主目录在发布后同步，新版本使用独立工作目录。
- 新命令、新状态、新字段、新依赖和新审批环节均为零。
- 运行时代码只同步发行版本常量；安装器流程、快照格式、角色投递和切片执行逻辑不变。
- 版本同步会触及发行清单、Skill 标题、安装与依赖说明及现有版本断言；历史发行说明不改写。
- 拆分质量仍由 Codex 判断；结构检查通过不能证明没有业务遗漏。

## 验证范围

以下案例用于核对规则能否给出合理的处理边界。当前记录为作者依据修改后规则完成的场景推演，不是独立模型行为实测，也不把文字检查计为运行验收。后续实际使用发现偏差时，按具体案例调整规则，不扩展评测框架或增加固定评分。

| 场景输入 | 本次推演的处理结果 | 核对结论 |
|---|---|---|
| 已定位设置页的一处错字，要求修正并检查显示 | 普通 Codex 任务直接修改；不建立 DLoop 档案，也不把修改和检查拆开 | 入口条件能保持小任务规模 |
| 新增收藏、列表查看和取消收藏；项目已有稳定存储接口 | “收藏并可在列表看到”形成可用闭环，再交付取消收藏；两项均包含所需界面、接线和验证；最终核对收藏后取消的连贯结果 | 可以按结果拆分，无需强制基础层任务 |
| 两个入口都修改同一份偏好设置，但数据归属尚未决定 | 先调查并在设计中明确权威数据与更新责任；再决定合并实现或分步交付，不能让两个实施者各自决定状态 | 共同依赖先于切片独立实施 |
| 详情页可能依赖未确认的接口字段 | 先调查接口事实；影响结果的字段仍未知时保留具体缺项，不能猜字段或将详情页从范围删除 | 结构性未知不会被任务清单掩盖 |
| 要求制作两个界面，只找到其中一个 Prefab | 对缺失目标记录调研结论；已授权的新界面在设计与实施范围中承接，独立工作继续，制作后才采集真实截图 | 缺资产不造成自动生成或范围丢失 |
| 原切片中的统计展示改由后续切片承接 | 计划保留原场景到新切片的对应关系，复查相关依赖；接受的历史成果沿用，最终检查统计与前置操作串联证据 | 重新切片不等于取消原承诺 |
