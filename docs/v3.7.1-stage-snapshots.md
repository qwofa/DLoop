# DLoop 3.7.1 中间态保存与阶段重做方案

## 版本与交付范围

按用户指定版本号开设 3.7.1，基于冻结标签 v3.7.0，并保留主分支公开文档与安装入口。当前为 frozen，由 `v3.7.1` 标签固定，快照保存、导出、恢复及工作流接入已实现，验证结果见文末；本次冻结不包含安装到用户项目。VERSION、release.json、Skill 描述和发布说明统一使用 3.7.1。

使用者是在 DLoop 作业中希望保留尝试、撤回修改或重做阶段的用户。最低可用结果是：每个正式阶段和实施检查点都能找到当时的真实文件；回退前保住当前现场；继续执行时文件、阶段、依赖和批准一致。保存自动进行，恢复由用户意图触发。

## 3.7.0 基线现状

- 实施开始时，现有修改占用会保存授权范围的完整文件内容，用于撤销本轮；所以当前并非所有位置都只存哈希。
- 实施检查点保存文件摘要、工作区防护摘要、契约和验证结果。固定候选及已接受产物也用摘要检查变化，不能从摘要还原文件。
- 现有人工回退支持保留现场、原范围返修、撤销活动实施；已接受成果通过新切片修改。尚无任意阶段或检查点恢复入口。
- Git 检查不自动提交、切换分支或修改暂存区；SVN 提交组只做本地归组。整体交付冻结后不解冻。

代码依据：src/FeatureArchive/archive_workspace.py、archive_workspace_close.py、archive_slice_flow.py、archive_candidates.py；行为依据：docs/v3.6.8-human-rollback.md、docs/v3.7.0-git-support.md。

## 推荐存储方式

SVN 和 Git 项目统一使用独立的本地 Git 裸仓库保存 DLoop 快照。每个作业一个快照库，放在项目 .scratch/dloop-v3/snapshots/<feature-id>.git，与可清理的角色视图、缓存分开。它是持久数据，正常缓存清理和卸载不应删除，清理完整作业时必须同时列出它。

保存只写这个快照库，不提交到项目 Git 分支或 SVN 服务器。项目仍使用原有 SVN/Git，快照库不配置远端。SVN 项目需要额外安装 Git；启动作业时检查依赖，缺少时在开始修改前明确报错，不能静默退化为只记哈希。

选择原因：本地 Git 提交可保存完整目录树并复用相同内容；无需 SVN 服务器账号、网络和大量中间修订，也避免维护两套快照存储。SVN changelist 仅是文件分组，不保存各阶段正文。首次版本不实现独立本地 SVN 仓库、SVN shelving 或远端自动备份。

技术依据：[Git commit-tree 官方文档](https://git-scm.com/docs/git-commit-tree)、[Git hash-object 官方文档](https://git-scm.com/docs/git-hash-object)、[SVN changelists 官方文档](https://svnbook.red-bean.com/en/1.8/svn.advanced.changelists.html)。上述后端选择是本方案的工程判断。

## 什么情况下保存

| 时机 | 保存内容与用途 | 是否必须 |
|---|---|---|
| 作业建立后、首次正式修改前 | 作业初始材料和已知受管范围起点，用于撤销整个作业的改动 | 必须 |
| 每个阶段开始前 | 固定阶段输入；与上一阶段结束相同时复用文件内容，但保留“阶段开始”标记 | 必须 |
| 阶段产物正式提交评审或等待用户确认时 | 固定用户和评审者实际看到的需求、设计、UI 图文及其状态，保留未通过版本 | 必须 |
| 评审或批准结果正式登记、阶段完成时 | 保存决定及其绑定材料，作为下一阶段输入；不捏造人工批准 | 必须 |
| 每个实施切片、每轮返修开始前 | 保存本轮代码与资源起点；先保存，再允许写入 | 必须 |
| 每次合法实施检查点登记时 | 保存当时实际正文和验证结果；验证失败、未完成或熔断也保留，并清楚标注 | 必须 |
| 固定候选提交、候选评审结论登记时 | 保留待评审版本、失败版本和接受结果，避免返修改掉被评审版本 | 必须 |
| 正式材料将被重新生成、替换方案或返修覆盖前 | 先保留旧稿；多文件连续更新作为一次受管操作，不逐文件生成快照 | 必须 |
| 用户要求暂停、交接、撤销、回退或重做时 | 在停止所有受影响写入后保存当前现场；没有变化可复用最近内容 | 必须 |
| 合法扩展受管范围、或后续切片首次触及新路径之前 | 保存新路径的首次修改前内容，之后才能授权写入 | 必须 |
| 最终集成结果登记、整体交付冻结时 | 保存最终文件、证据和正式封存结论，作为交付终点 | 必须 |
| 用户说“这里存一下”“留个版本” | 保存当前位置，可附业务名称，不要求阶段完成或验证通过 | 必须 |
| 状态查询、读取文档、重复投递相同请求、相同状态重复验证 | 不生成重复保存点；已有请求返回同一保存点 | 不保存新点 |
| 每次键盘输入、每条修改命令、每次截图、定时轮询 | 不自动保存；在最近的正式检查点或发布动作统一保存 | 不单独保存 |

阶段包括现有需求、设计、UI（适用时）、切片计划、实施与验证、最终交付等实际开放阶段；没有启用的阶段不生成空快照。术语以现有阶段登记为准，不另建一套阶段命名。

普通公开操作保存一次结果；会撤销实施或覆盖旧材料的操作先保留现场，再保存操作结果。未变化的重复保存可复用已有点。文件内容不变而评审或阶段状态变化时，仍产生新的业务保存点；Git 复用文件对象。快照存在仅表示“保存了”，不表示“验证通过”。

进程被强制结束时无法保证额外保存最后一刻：只承诺已成功登记的保存点可用。再次进入时先检查现有现场，保存可读取的当前内容，再决定继续或恢复。长阶段应在完成一个有意义的工作段落、准备进入下一段可能覆盖成果的工作前登记检查点；不承诺逐条工具调用恢复。

## 每个保存点包含什么

1. 文件内容：本作业累计管理的代码、配置、场景、Prefab、资源及配套 .meta，正式需求和设计材料、UI 模型及其引用截图、必要验证证据。二进制文件也保存原始字节；新增、删除、重命名以及缺失路径均有明确记录。
   UI 明确登记的原始需求来源也按原始字节保存为只读输入；导出清单将原路径对应到 `inputs/` 下的文件，缺失来源明确标记。来源登记本身不授予恢复覆盖权限，重做或派生作业可以从导出材料取用正文。
2. 工作流事实：阶段和轮次、契约版本、任务包、检查点、候选、评审、批准及其有效性、验证结论、依赖关系。保存历史事实，但恢复时不原样复活历史执行身份、租约和锁。
3. 保存点信息：所属作业、单调递增序号、时间、业务名称、触发原因、前一保存点、恢复来源（如有）、文件内容摘要和快照提交定位。
4. 仓库上下文：源项目身份、Git 修订及实施起点防护信息，或 SVN 工作副本修订、必要属性及增删归组信息。它们用于核对和有范围的恢复，不备份整个 .git/.svn 管理目录，也不恢复或覆盖源 Git 索引。

不保存整个工程，不收集其他作业或无关文件。Unity Library、Temp、构建缓存、可重新生成的角色视图、锁和快照库自身不进入快照。明确属于交付的被忽略文件仍保存，不能用项目忽略规则排除真实产品资源。屏幕截图按正式引用保存，临时试拍不单独归档。

本作业开始前已有的未提交修改是基线的一部分；撤销只能撤销 DLoop 在这之后做的修改。对于后续才纳入的路径，在首次触及前补存原始内容；恢复到更早保存点时，对当时尚未纳入的路径使用该首次基线，而不是误认为它们当时不存在。目标恢复范围是目标与当前轮次的累计受管路径并集，不能漏掉后续新增的文件。该规则依赖现有“受管内容不被外部直接改写”的工作前提。

以快照库中的原始文件对象保存内容，不经过项目的换行转换、清理过滤器或 LFS 指针替换；恢复后用现有文件内容摘要核验实际字节。对未来阶段必需的资产，保存实际内容，不能只保存需要联网取回的引用。

## 如何回退和重做

用户仍用自然语言选择，例如“回到第二个切片返修前”或“重做 UI 设计”。列表显示时间、阶段、保存原因、验证结果和业务名称；恢复预览另外列出受影响文件、切片及新轮次。

### 查看或取出旧文件

把指定保存点导出到独立目录，可查看、比较或提取文件；不改变当前工作区和流程。仅要查看历史时采用此方式。导出内容包括覆盖范围清单，不声称是能独立构建的完整工程。

### 恢复并继续、重做某个阶段

1. 停止当前执行，取得现有单线修改资格，检查目标属于本作业当前版本；生成文件和阶段影响预览。用户已经明确选择目标和处置范围时直接按意图执行，仅有“回退一下”而目标不明时才询问。
2. 必须成功保存回退前现场。保存失败则停止恢复，当前文件不动。
3. 恢复目标文件。回到某个中间检查点可作为新的尝试起点；“重做某阶段”默认使用该阶段开始前的输入，而不是恢复该阶段已经完成的状态。
4. 历史记录保持不变，追加新的执行轮次并注明来源。旧执行身份和修改占用失效，新一轮重新取得身份；目标之后的候选和结论保留为历史，不能继续作为当前通过凭据。
5. 按现有依赖规则刷新受影响材料和批准；未改变输入的上游批准可以复用，需求、架构或交互变更导致相关批准失效时，按既有规则重新确认。文件恢复成功后重新计算当前工作区摘要，不照搬旧摘要。
6. 只重跑被恢复或重做影响的验证；最终交付仍须对当前完整结果核验。恢复完成时再保存一个点，明确“已恢复、待继续/验证”。

若第二个切片依赖第一个切片，回到第一个切片之前会使两者之后的当前成果退出有效结果集合；首次版本不尝试自动挑选并合并保留第二个切片。无关阶段能否保留由已登记依赖决定，不由文件名相似度推测。

待评审候选通过“结束本次尝试并从保存点重开”路径恢复，保留待评审历史，不伪造评审失败来解锁。已接受候选也不能改写成从未发生；重做以新轮次承接，评审记录继续可查。

### 已冻结作业

冻结操作必须保存最终状态，保存失败时通过恢复入口补齐登记。冻结后仍可查看或导出任何保存点；需要继续 DLoop 时创建新的作业并引用旧保存点作为来源，重新登记目标与范围、处理依赖与批准，原作业保持冻结。不通过旧状态文件覆盖实现“解冻”。

源仓库提交、更新或分支切换导致基准已变化时，旧保存点仍可导出，但不自动原地覆盖或合并；要在新基准继续，走新的变更作业。首次版本不做跨版本作业恢复、跨机器会话续跑或任意历史提交重置。

## 一致性与失败处理

- 正式状态变更应由工具负责保存；Skill 负责在编辑阶段开始和覆盖旧产物前调用保存入口，不能只在说明里提醒“记得保存”。
- 复用现有工作区锁；正式操作先登记待保存标记，完成业务写入后用 Git 提交固定正文与对应状态，再清除标记，全部成功才报告完成。恢复另外登记回退前保存点和租约，失败时据此还原。失败遗留但未固定引用的对象不显示成有效保存点，相同请求重试不产生重复业务记录。
- 快照提交不包含它自己的提交编号；定位映射在外层登记，防止自引用。保存的工作流投影不包含快照库或可重建的快照索引。
- 多文件变更已发生但保存失败时，保留当前文件并阻止进入下一阶段，允许重试；不得报告“已保存”。恢复期间失败则按原事务恢复回退前文件和业务状态。强制终止发生在恢复途中时，依据持久恢复记录完成或撤销该次事务，在收敛前不得开放新实施。
- 保存过程不改变源 Git 的分支、HEAD 和索引。恢复正文也不整体重置索引；保留既有暂存内容并重新核对当前差异。SVN 恢复受影响路径的正文及 DLoop 改变的纳管、必要属性和归组状态，不执行全工作副本 revert；Git/SVN 均不执行远端提交。
- 当前作业内全部保存点默认保留，不设置自动过期和自动裁剪；同内容复用对象。空间不足时说明失败并保留现场，不静默删除旧点。大二进制的多轮变化仍会占空间，界面显示作业快照占用，用户可在交付后显式导出或清理整份历史。
- 快照仅在本地不等于异机备份；本版不建设远端同步。缓存清理、作业删除、卸载、分享导出对快照的处理必须逐项明确，默认分享产物不自动携带整份代码历史。

## 实施顺序与验收

1. 先完成独立本地 Git 存储、保存/列表/导出、持久目录与清理边界，再接入作业初始、阶段边界、全部实施检查点和最终冻结。此步可验证内容确实可取回，但不算整个需求交付。
2. 完成回退前保存、范围恢复、失败回滚和新轮次登记，覆盖活动实施、待评审候选、已接受切片的恢复及阶段重做。
3. 补齐自然语言路由与状态展示，明确冻结后新作业入口；完成真实 Git/SVN 验证和安装、校验、卸载回归后才允许冻结发行。

必要验收用例：

- 按公开工作流走完一轮，所有应保存的阶段和检查点都有可读的文件及对应业务状态；失败检查点也能导出，且不显示通过。
- 真实 Git 与 SVN 临时项目包含中文/空格路径、已有未提交修改、增删改名、二进制及 Unity .meta；反复保存和恢复后逐字节一致，无关文件不变。
- Git 含既有暂存和未暂存修改、worktree、项目子目录；保存和恢复不改变原索引内容及分支。沿用现有子模块范围限制。
- SVN 包含 DLoop 新纳管文件、目录、归组及必要属性；恢复后文件和版本管理状态相符，未发起服务器提交。
- 切片一改文件 A，切片二再改 A 并新建 B：回到切片一结束时 A 正确、B 撤销；后续首次纳管的既有文件恢复原基线而不是被删除。
- 需求或 UI 方案重做后，受影响候选、评审和批准不能支持当前交付；未变上游批准仍按现有规则复用，历史可查。
- 固定候选尚未评审时可合法保存并重开；已接受切片重做保留旧历史、使依赖下游退出当前有效集合。
- 回退后仍能从“回退前现场”返回，重试同一保存请求不重复；保存失败阻止推进，恢复失败或过程中终止后文件与正式状态能收敛。
- 缓存清理、同版重装和卸载保留快照历史；冻结后可导出并作为新作业来源，原作业不解冻；源仓库基准变化时不盲目覆盖。
