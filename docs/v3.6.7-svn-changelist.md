# DLoop 3.6.7：同一交付项的 SVN 产物归组

按用户指定版本开发 3.6.7，保留 3.6.6 实施前的 UI 交互确认能力。用户于 2026-09-10 授权冻结、创建 PR 并合入；合入以已冻结的 `v3.6.6` 主分支为基线，当前为 `frozen`，由 `v3.6.7` 标签固定。本次冻结不包含安装到用户 DEV，下文保留开发阶段验证记录。

## 用户可观察行为

- DEV 等 SVN 项目中，同一交付项的代码、Unity 资源及 `.meta`、需求与设计文档、截图、实施和验收材料、正式工作流状态、摩擦日志、共享索引及导出的分享材料，统一放入一个本地 SVN 提交组。
- 协调者从策划文档名称概括业务主题作为创建交付项时的标题。组名使用“业务主题 [交付标识]”，例如“建筑交互策划 [building-interaction]”；多份策划文档提炼共同主题。同名组含无关文件时自动加序号，之后所有切片、返修和恢复沿用已确定名称。
- 新文件先纳管再归组。已经存在的修改保持原内容，混合原有修改的文件随结果说明；无关文件保留原组。缓存、锁文件和工作区恢复缓存不作为正式交付物纳管。
- 只整理本地提交组，不执行 SVN 服务器提交。SVN 不支持把目录加入提交组，返回新增、删除等关联目录路径，提醒实际提交时一并处理。
- 非 SVN 项目跳过本项规则；本版不扩展原有实施工作区的版本控制支持范围。

## 实现

新增公开命令 `sync-svn-changelist --feature-id <id>`。项目与档案根由安装位置确定，文件来源为当前规范档案、该交付项的分享目录、既有候选的实际差异、当前修改租约的实际差异及已登记产物。没有对工作副本全部改动执行递归纳管或归组。

组名、文件清单及原有修改说明保存在交付档案的 `svn-changelist.json`，该记录也归入同组。整理使用明确文件路径，检查实际 SVN 分组结果；部分操作失败保留已完成的本地整理，修复具体阻碍后可重复同步，不声称已经完整归组。正常撤回切片后，下一次同步取消已撤回新增文件的纳管状态，以及已恢复文件的删除调度，保留恢复的原有正文修改。共享索引与摩擦日志是跨交付项共用文件，SVN 只能按整文件归组，因此由最近整理的交付组携带。

检查点通过前置合同和范围检查后自动整理产物，再取得 SVN 状态用于固定候选。Skill 同时要求初始化、阶段材料完成和最终收尾后同步；实施与协调者取得对应规则，只读评审者不执行整理。新增产品文件需要重新形成最终检查点；补充档案、索引和分享材料不要求重跑产品验证。

正式文档纳管后会持续更新，因此工作区产品变化检查排除 DLoop 管理的档案与运行状态，保留稳定 UI 模型的检查。目录纳管本身不作为产品变化，目录属性变化仍参与检查。SVN 修订仍绑定，修订字符串中的本地修改标记不重复作为变化来源；实际产品文件状态和正文摘要继续参与绑定。文档新鲜度和审批仍由原有档案规则负责。

元数据归组只补齐产物文件自身的 `.meta`，不沿父目录自动收集；新增目录的元数据通过授权范围内的实际改动纳入。既有父目录元数据保留原有分组或未纳管状态，避免归组自身产生范围外变化而阻断正常撤回。补齐关联文件后统一核对实施前的修改，关联元数据含原有修改时同样记录并在后续同步中保留说明。

Windows SVN 调用使用无控制台子进程，避免本机客户端在继承宿主控制台时错误转换中文参数；不改变系统语言、代码页或 SVN 配置。

## 验证范围

通过项目内安装路径运行完整公开命令流程，验证检查点自动归组、候选提交与独立评审、最终批准、收尾再次同步不使最终批准失效，以及切片中断恢复后的再次整理。测试只使用临时仓库，不修改真实 DEV 或向真实 SVN 服务器提交。
