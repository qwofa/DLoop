# DLoop 3.6.3：当前任务路由与单次读取效率

基于冻结标签 `v3.6.2`，当前为 `frozen`，由 `v3.6.3` 标签固定。本次修复既有工作流行为、精简查询输出和澄清实施权限，因此使用补丁版本 3.6.3；不覆盖冻结版本，不改变档案格式、六阶段、单一 SVN 修改占用或人工业务批准。下文保留各开发批次当时的验证记录，最终冻结结论见末节。

## 已授权范围

本次实现对应前次分析的第 1、2、5 项：

1. 协调者登记后续任务包后，当前实施、候选评审与返修仍应正常交接。先定位当前修改占用对应的执行任务，再处理其他待收敛执行；只有没有执行任务时才选择未来待办。未来草稿和就绪任务不得制造当前执行歧义；多个待办没有唯一选择时仍交给协调者判断。
2. 普通检查点在一次事务内复用已取得的授权范围与 SVN 防护快照。实施角色视图、批准判断、交付视图和材料选择复用同次校验的档案与状态。每次新命令重新读取，不保存跨命令缓存，不取消批准新鲜度、材料正文、候选与工作区变化检查。
3. 授权写入范围内保持已批准外部行为、公共接口、跨模块状态归属和安全约束的内部整理，由实施者判断并接受候选评审。私有辅助逻辑、等价校验顺序、错误处理收拢不单独触发架构批准；不扩大产品写入范围，不授予任意重命名或整文件格式化权限。真实公共合同变化仍走设计评审。

第 3、6 项原分析建议尚未实现，第 4 项按用户反馈不推进，见 [待评估改动计划](workflow-change-proposals.md)。本次未启用 DLoop 管理自身开发，没有生成项目交付档案或替用户作业务批准。

## 实现范围

- 当前动作路由优先选择修改占用对应的执行，未来待办保留在既有切片方案和状态中，不增加调度状态。
- 检查点重复请求判断与正式登记复用同次快照；重复提交和工作区变化仍按当前事实判断。
- 批准查询保留原入口，增加消费已校验事实的内部投影能力；角色装配直接传递已读取状态，不引入通用缓存框架。
- 协调者规则与独立实施、设计评审、候选评审的角色材料同时澄清内部实现边界。
- 版本、Plugin、两个 Skill、工具和 Unity 包元数据保持 3.6.3 一致；安装流程本身未改动。

## 验证

新增回归覆盖：

- 当前实施旁存在后续草稿和就绪任务时，实施交接、独立候选评审及失败返修仍定位当前任务。
- 错误执行身份仍被拒绝；没有当前执行而存在多个待办时，不自行选择。
- 单次实施角色读取只校验一次档案、加载一次工作流状态；下一命令能够读到通过公开命令变更的批准结论。
- 每次检查点只取得一次授权快照和一次 SVN 防护快照；重复请求保持幂等，后续实际修改产生新检查点。

验证结果：

- 新增 4 项回归全部通过，包含实际候选提交、独立评审失败及返修交接的工具闭环。
- 工作流全量 322 项：320 通过、1 项源码环境下的安装态检查跳过、1 项旧评审规则文字断言失败。该断言已按新的公共合同边界同步，相关 11 项重新运行全部通过；没有改动生产逻辑来迁就旧断言。
- 发行、安装和卸载集合 36 项：35 通过，1 项真实 Unity Editor 采集因未配置环境跳过。使用临时项目，未安装到目标项目。
- 两份 Skill 结构校验通过；检查器默认 Windows 编码首次读取失败后，使用显式 UTF-8 模式通过。修改的 Python 文件语法和差异空白检查通过。
- 真实 SVN 隔离复核使用当前工具和公开命令，结果保存在 `local-artifacts`。后续草稿存在时，当前实施角色无阻断且交接就绪。

同一类预批准隔离任务的读取计数如下；这些是实际调用次数，不是模型 token、全项目耗时或全部文件读取总数。

| 操作 | 3.6.2 分析实测 | 3.6.3 复核实测 |
| --- | --- | --- |
| 普通检查点的目标文件读取 | 2 次 | 1 次 |
| 普通检查点的 SVN 状态扫描 | 2 次 | 1 次 |
| 一次实施角色读取的档案校验 | 4 次 | 1 次 |
| 一次实施角色读取的工作流状态加载 | 7 次 | 1 次 |

以上计数指直接实施角色读取；省略执行身份的交接准备仍有独立身份定位读取，本次没有把全部交接、最终批准和工作区检查合并成一个总缓存。

本次不以减少函数调用或返回字节数宣称模型生成代码质量提高，也不以局部复现代替完整 Unity 项目交付。

## 下游上下文精简：第一批

用户授权基于 3.6.2 验证结果实施第一批上下文精简；沿用当前 3.6.3 开发版本，不改冻结的 3.6.2，也不推进上文待评估的范围补充或宿主验证策略。

- 协调者保留全局交付视图和动作路由；实施、候选评审、冷读、设计评审与最终验收只取得当前阶段、阻断及各自完整角色合同。失败时仍提供具体原因和交回协调者的下一动作。
- 完整档案、批准、新鲜度、身份、候选与集成确认检查照常执行，只在最终输出时裁剪全局方案、其他切片结论和调度信息。
- 交接字段说明只在程序内部定义，由交接准备生成消息；最终验收的集成确认定位仍正常交付。实施写入范围只保留任务包中的正文。
- 额外劳动记录保留命令、已知定位、触发条件和不阻断交付的约定；需要填写时通过现有规则入口读取详细说明。没有新状态、缓存或摘要文件。
- 人格、角色判断规则、必要任务事实和材料正文读取范围保持原有安排，本批不实施正文裁剪或 agent 配置迁移。

专项回归 73 项全部通过，包含五类下游交接、返修、其他待办存在时的当前任务材料隔离，以及按需读取说明后实际记录额外劳动且不改变业务状态。最初记录专项测试的临时项目未带 Skill 资源，补齐安装布局后通过；没有为测试放宽生产检查。

## 协调者状态查询精简

根据目标项目 中已安装的 3.4.2 状态产物评估，进一步精简状态查询输出；完整状态文件、任务包历史和恢复数据继续保留。实现仍位于 3.6.3 开发版本，未修改 Dev 的安装或状态产物。

- 指定交付项的 `workflow-status` 默认只返回状态、交付项身份和一份 `delivery_view`。批准、切片与方案结论直接消费该视图，不再重复返回顶层副本。
- 修改占用只提供交付项、任务包、工作区、占用状态、执行身份和当前候选身份；指定交付项时位于统一视图内，未指定时作为全局占用摘要返回。
- 增加 `--include-details`，排查时按需展开完整工作流状态、修改占用基线及最终门禁明细。完整状态包含原有历史，不增加新的状态文件或摘要同步机制。
- 默认和展开模式执行相同的原有检查，当前阶段、阻断和下一动作一致；查询不写回状态，实际中断仍使用完整恢复数据还原文件。
- 已同步协调者 Skill、执行说明和命令文档，以及消费状态输出的既有回归断言。

## 最终门禁修复与冻结

审查复现：交付 A 已进入最终验收，交付 B 通过正常命令取得工作区修改占用，尚未修改业务文件。A 的默认状态原来仍提示最终批准；若 A 已批准，则提示可以冻结。实际操作会被全局修改占用阻断，但阻断原因仅在展开明细中出现。

统一交付视图现在在提示最终批准或冻结前核对现有执行门禁。有阻断时显示具体原因、停止提示推进，也不新增人工批准点；占用释放后重新读取，恢复正确下一动作。协调者上下文与状态查询共用修复，持久状态和恢复数据保持原有结构。

新增回归使用隔离项目与公开命令覆盖未批准、已批准两个阶段：默认与展开状态一致，协调者取得同一阻断，最终交接或冻结被拒绝，中断另一交付项并释放占用后恢复推进，最终实际冻结成功。测试不直接改写受管执行状态。

冻结验证：工作流全量 328 项，327 通过、1 项源码环境安装态检查跳过；发行、安装和卸载集合 36 项，35 通过、1 项真实 Unity Editor 采集因未配置环境跳过，合计 362 通过、2 跳过。两份 Skill 结构、20 个修改的 Python 文件语法及差异空白检查通过。专项用例最初复用了已结束切片的启动入口且未填齐冻结材料，按正常重试入口和正式冻结输入完善夹具后通过，未放宽生产门禁。

3.6.3 按用户授权冻结，由 `v3.6.3` 标签固定；本次不安装到目标项目。已有读取次数与响应字节对照的结论仍仅限对应样本，不据此声明完整模型任务提速或代码质量提升。
