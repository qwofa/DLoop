# DLoop 3.5.0：交接前材料准备

## 目标与版本边界

基于已冻结的 v3.4.5 开发 3.5.0。新增交接前材料准备能力并调整角色完成条件，按新增功能使用次版本；2026-09-07 完成设计评审和验收，当前状态为 frozen，由 `v3.5.0` 标签固定。冻结不包含向用户项目正式安装的授权。

上游提交待交付结果，程序检查并装配下游材料；缺项时在上游原上下文中补齐，材料就绪后协调者再启动下游。下游保留独立完整性与业务正确性核对。程序不推断业务决定、不虚构测试或批准事实。

## 正常执行路径

1. 协调者提交任务包并启动切片时，工具在使用身份和取得租约前检查所引用的完整文件与精确章节，并加入遗漏的正式设计入口。缺项一次返回来源、具体章节与补齐责任；检查通过才进入活动状态。
2. 实施者提交候选时，工具在固定候选前用相同规则装配评审材料。材料缺项保留活动身份、当前成果和租约；实施者在原上下文补齐，产品变化仍按原验证策略更新检查点，再次提交。
3. 协调者在创建每个下游上下文前调用 `prepare-handoff`。准备复用目标角色的完整合同，返回 `handoff_ready`；失败不返回任务消息或部分角色合同，成功返回最小任务消息、下游读取命令和装配后的角色视图。
4. 下游只接收生成的任务消息与读取命令，使用 `context-summary` 独立取得正式事实。实施对话、作者预期和冷读答案不进入评审输入；准备通过不替代评审通过。
5. 返修启动在切换身份前检查材料和既有评审快照，并返回完整原候选、问题集与保守重验范围。完整投影只在返回值中，档案仍只保存既有引用与事实。

设计评审使用 `--action design --role design-review`；冷读使用当前动作、`--role cold-read`、入口问题及可重复的允许材料参数；实施与候选评审使用 `--action implementation`；最终验收使用 `--action validation --role final-review` 并提供集成确认文件。全部调用显式指定交付项。

实施角色的完整合同在现有启动命令成功后准备；启动命令已经在改变状态前完成材料检查。评审准备可生成尚未使用的身份建议，但不登记或预占它。准备失败后的具体业务处理仍由协调者判断，不由程序推进状态。

## 改动范围与成本控制

- 共用材料装配模块替代原来只检查指定章节的逻辑，同时服务实施启动、候选提交、返修和下游角色视图。
- 新的准备命令复用现有阶段、身份、新鲜度和最终绑定规则，不另建材料合同。
- 更新入口、实施、独立评审和验收规则，明确“成功提交才结束”和“就绪才创建下游上下文”。
- 不增加交接持久状态、材料副本、后台调度、自动重试、会话恢复或跨版本兼容。CLI 沿用既有摩擦记录，不将其当成交接事实。

程序能强制阻断正式提交与启动命令；宿主中的下游上下文仍由协调者按 Skill 创建。此版本没有接管宿主调度，因此不声称能从程序层禁止任何提前创建上下文的行为。原上下文意外丢失继续使用既有中断流程。

## 验收

- 启动发现多个可独立判断的材料缺项时一次返回，不使用身份或取得租约；补齐后同一启动输入可成功。
- 实施在授权文件修改中遗漏被引用章节，提交必须拒绝并保留原执行；补齐并重新验证后可提交。
- 前置准备和下游取得相同材料、候选与返修事实；重复准备不改变工作流状态或消耗评审身份。
- 冷读输入不全、设计占位、缺集成确认、自评或阶段不符时不提供可执行的部分合同。
- 就绪不产生业务批准，候选固定、独立评审、事务和安装卸载保证继续有效。

自动化验证覆盖公开命令与既有状态机。宿主模型实际遵守交接顺序的效果，以及真实耗时和上下文节省，需后续真实作业记录验证，不用模拟 trace 冒充实测收益。
