# DLoop 3.3.7：DloopUI 配置接入决策

## 决策

DloopUI 以显式配置 `dloop-ui-v1` 接入 DLoop，不建立第二套工作流。`$dloop` 初始化时不带配置，保持普通产物；只有 `$dloop-ui` 初始化时选择该配置。普通 Unity/UI 自然语言不构成选择依据。

UI 完整事实只保存在交付项根目录的 `ui-model.json`。DLoop 的 `workflow-state.json` 只增加可选配置标识、模型相对路径、模型和审计摘要、计数摘要。配置字段缺失在当前合同中代表普通 DLoop；本版本不读取、转换或迁移旧版本 UI 文档。

## 模块边界

核心工作流只暴露初始化、校验、阶段检查和同步四类通用配置接口，并负责档案边界校验、状态提交与原子写入。DloopUI 作为当前唯一配置静态登记到这些接口，独立拥有 UI 模型、审计、视图和错误语义。只有出现第二个真实配置时，才评估引入动态发现协议。

静态登记同时保存可同步阶段，以及需求确认、实施准入等通用业务检查点到配置内部阶段的映射；未登记的检查点不调用适配模块。同步接口只向核心返回通用的 `PASS` 或 `BLOCKED` 状态，配置专属诊断和公开摘要仍由适配模块拥有。普通 DLoop 命令不加载 DloopUI 适配模块。

UI 模型的初始结构、来源材料证据、数量字段、稳定标识、审计和渲染统一由一份运行时拥有；DLoop 初始化把用户提供的需求或既有 DLoop 资料交给显式配置登记，并立即形成与初始模型一致的模型、审计和数量摘要。删除独立模板和独立初始化入口，避免形成第二事实源。插件中的 Skill 与运行时由载荷清单声明，安装器不再逐项硬编码 DloopUI 文件。

## 阶段叠加

| DLoop 既有阶段 | DloopUI 追加内容 |
|---|---|
| 需求 | 集中 Prefab 术语视图；既有需求批准同时检查术语确认是否有效 |
| 调查 | Prefab 清单、计划新增声明与真实资产证据视图 |
| 设计 | 交互、显示状态、UI 去向、外发意图与资源依赖视图 |
| 计划 | 逐 Prefab 规划和规划审计视图；进入实施前实时重跑计划审计 |

人工审批仍只有 DLoop 的需求、架构和最终批准。UI 审计只作为机器门：术语身份、名称、归属或数量变化会使需求批准在实时视图中失效；计划模型或证据变化导致审计阻断时，实施启动和阶段投影都退回计划补充。

用户要求停在规划边界时，先完成七份视图、计划文档与 UI 审计，然后不创建或启动任何实施切片。DLoop 原有投影会在零切片时等待“是否还有已批准切片”的人工判断；这表示流程已到实施边界，不表示执行过 Unity 产品实施。恢复时从同一状态和模型继续，同步只补齐缺失 ID，不改写已有 ID 或仍有效的确认。

## 发行与安装

版本选择 `3.3.7`：本次不改变档案主结构、阶段集合或审批类型。单一 `dloop` Plugin 同时包含两个显式 Skill 和共享运行时；安装锁一次拥有、校验和卸载全部模块。安装器只管理当前版本：同版本可幂等重装，其他版本在读取受管内容前拒绝。仓库不保留旧版载荷，也不运行交付档案迁移。

Plugin 只包装现有核心和 UI 配置运行时，没有为了包装重写 DLoop 状态机。第一期源目录在验证完成后改为指向本 Plugin 中 `dloop-ui` Skill 的 Junction；原发现 Junction 继续经该稳定入口解析到唯一活动源，并保留可回滚备份。
