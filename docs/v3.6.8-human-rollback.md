# DLoop 3.6.8 人工回退

## 版本与范围

用户指定以 3.6.8 实施本需求。本版基于 3.6.7 冻结源码提交 `历史提交已脱敏` 开发，使用补丁版本修正既有流程的意图分流与操作指引；不新增命令、状态或档案格式。用户随后确认将交付自动冻结加入同一未冻结的 3.6.8 开发版；复用生命周期命令并增加集成确认参数，调整封存门禁与收尾指引，不增加解冻。2026-09-10 经用户授权冻结，当前为 `frozen`，由 `v3.6.8` 标签固定；本次冻结不包含安装到目标项目。隔离目录从已核对的冻结提交创建，冻结前已同步远端 `v3.6.7` 标签及主分支。

与 README 稳定设计意图保持一致：用户通过对话决定，协调者复用确定性工具维护正式事实；本版不修改该意图，不扩大到外部越权改写或跨版本恢复。

## 需求与方案

使用者是正在通过 DLoop 开发功能、发现方案或实现需要调整的用户。用户说清要改变什么即可，协调者负责识别暂停、原范围返修、撤销本轮或已接受成果变更，并保持文件、执行身份、方案和批准一致。

普通 DLoop 与 DloopUI 入口都将人工回退路由到已有 `slice-release` 规则投递；具体约定仅维护在实施规则的“人工回退”一节。先停止受影响执行，再判断成果处置；当前执行收口后才正式更换方案，文档语义变化和批准失效复用原流程。

暂停保留成果和租约；明确撤销活动实施才调用会恢复执行前基线的中断。已接受成果通过新变更切片修正，历史不改写。待评审候选不能伪造评审失败或故意制造漂移来获得撤销资格；没有合法处置入口时保留现场并说明限制。本版不提供任意阶段、检查点或已接受候选的一键恢复。

## 验收场景

| 用户要求与当前事实 | 预期处理 |
|---|---|
| “先停一下，代码保留，讨论设计”，当前正在实施 | 停止写入，保留成果、身份和租约；不提交会恢复基线的中断 |
| “实现太绕，目标不变”，当前活动实施或评审未通过 | 原身份继续修改或原范围返修，不自动重开需求审批 |
| “这轮不要了，恢复到这轮开始前”，当前活动实施 | 按原执行身份中断，恢复授权基线；原范围重试或放弃后重新规划 |
| “这个方案不要了，重新设计”，当前没有实施占用 | 修改相关正式材料，确认语义变化，按依赖刷新下游；仅重办失效批准 |
| “上个已经接受的功能撤掉” | 保留候选和评审历史，新增变更切片核对后续依赖，重新验证实际结果 |
| “回退一下”，上下文无法确定代码处置 | 只询问缺失的处置范围，等待期间保留现场 |
| 当前固定候选尚未独立评审，用户只说取消 | 不伪造失败或修改候选；按现有资格处理，无合法入口时明确限制 |
| DloopUI 已确认交互被修改 | 回写场景与受影响标注，按已有交互批准规则复审 |

## 交付自动冻结（本轮追加）

用户在本任务明确确认：所有计划内切片完成并通过整体交付检查后，由工作流自动封存；之后用户自行或通过普通 Agent debug，不继续管理原 DLoop 作业。封存表示开发交付记录结束，与人工验收分开，不要求补一句“冻结”或伪造最终批准；暂不支持解冻。

- 当前批准方案全部切片须已接受或明确放弃，至少保留一个已接受实现候选；已声明而尚未登记任务包的切片不能被遗漏。协调者仍反查完整需求，必要集成验证和独立交付评审完成后记录实际结论。
- 复用当前集成确认检查候选集合、独立评审和最终工作区。需求、适用的架构与 UI 交互批准仍有效；用户已退回当前结果时阻断自动封存。用户明确要求先验收或暂停时，协调者遵从，不机械收尾。
- 仍要求正式文档完整新鲜、验证通过、未验证边界与残留风险明确。最终人工批准缺失不阻断封存，已有决定原样保留；旧决定已失效时如实显示，不恢复为已接受。
- 冻结后整理 SVN 提交组并报告开发交付、人工验收和验证范围；冻结不等于代码锁定、服务器提交、版本发行或安装。后续普通调试不改变历史结论、不启动 DLoop；需要新的 DLoop 交付时另建档案。

追加验收：无人工最终批准仍可冻结且不写批准；未登记的计划切片、活动占用、陈旧集成确认、未完成文档和失败验证仍阻断；封存后普通代码修改不使历史交付失效；只读档案仍拒绝重新激活。
