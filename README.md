# DLoop

**为 Unity 长任务设计的 AI 开发工作流：减少过程干预，让人集中审核关键决定。**

DLoop 基于 **Codex + Unity MCP**，把长任务从需求梳理、项目调查和设计，推进到实施、独立评审、返修与验证。它的目标是减少人反复跟进和交接的负担，降低需求遗漏和实现偏离预期的概率。

你提供需求，在关键节点集中审核方案；工作流在已确认范围内持续推进，并用**精简、易读的文档和真实界面标注**，帮助你判断“需求有没有漏，设计是不是我想要的”。



## 它能帮你做什么

- **把长任务持续推进下去。** 组织调查、设计、分步实施、独立评审和返修，减少手动拆任务、转交上下文和反复催促。
- **把人的注意力集中到审批。** 汇总需要判断的范围、交互和关键取舍；已确认范围内继续执行，出现影响预期的新变化时再交回给你。
- **减少漏需求和需求偏移。** 从原始需求提取业务场景，贯穿设计、实施与评审；验证时回到原场景检查结果和差异。
- **让审核文档短而清楚。** 优先呈现目标、操作、效果、关键条件和待决定事项；过程细节保留查阅入口，方便你集中判断设计是否符合预期。
- **保留中间成果并按阶段重做。** 自动保存正式状态与检查点；需要调整方向时可先保留现场，再恢复历史或重做阶段。SVN 项目也使用本地 Git 快照库。
- **让 UI 交付看得清。** DLoopUI 实施中补齐有依据的交互，完成后用固定 HTML 模板集中展示截图、操作、反馈、结果和验证情况，再进行验收。

适合需要跨多轮执行、分步实现和验收的 Unity 功能开发。当前依赖 Codex 与 Unity MCP，项目使用 Git 或 SVN。

## 安装

需要 **Windows、Python 3.10+、Codex、已连接的 Unity MCP、Git 客户端，以及 Git 或 SVN 项目**。Unity MCP 不限实现或版本，但须满足当前项目操作与编辑器内采集所需能力。首次安装请先完成[依赖准备与连接检查](docs/dependencies.md)，再在 Unity 中打开目标项目。

在**目标项目根目录**打开 PowerShell，运行：

```powershell
irm https://raw.githubusercontent.com/qwofa/DLoop/main/install.py -ErrorAction Stop | python -
```

上面的一行入口安装公开主线指定的发行版；本版入口固定下载 `v3.8.1` 标签。入口会准备项目、安装 DLoop 与 DLoopUI，并校验结果。看到 `DLoop installed and verified.` 表示项目内载荷安装并校验成功。本地及离线方式见[安装说明](docs/installation.md)。

随后在 Codex 中打开这个项目，选择下面任一入口开始。Codex 和 Unity MCP 是已有环境依赖，本命令安装的是 DLoop。

## 使用教程

### DLoop：推进一项长任务

在 Codex 中输入 `$dloop`，附上需求文档，或直接描述目标：

```text
$dloop
根据我提供的需求文档完成本次功能。
先整理业务场景供我确认需求，再推进调查、设计、实施、评审和验证。
```

工作流会整理需求、调查现有项目，并在需要你决定时提供可审核的材料。你可以直接说：

```text
保留已经确认的交互，其余按这个方案继续。
```

需求确认后，工作流继续调查、设计、拆分实施、安排独立评审并处理返修；重大架构取舍按需确认。你无需手工逐条调度内部步骤；出现需求变化、关键取舍或真实阻塞时，再参与决定。

### DLoopUI：实施中补齐交互，完成后集中验收

涉及 Unity 界面、布局或交互改动时，使用 **DLoopUI**，实际入口是 `$dloop-ui`：

```text
$dloop-ui
根据我提供的需求文档修改相关界面。
结合相关后端、已有代码和实际界面补齐有依据的交互，
完成实施与验证后，用统一 HTML 展示结果供我验收。
```

DLoopUI 会匹配已有 Prefab，通过 Unity MCP 采集截图并保留内部设计。实施中补齐原范围内有依据的交互，最终从完整需求查实现、从实际实现查交互说明。统一 HTML 把可缩放截图与清晰文字分开，点击编号和说明可相互定位，集中审核：

- 哪个位置会变化，哪些现有表现继续保留；
- 用户执行什么操作，界面给出什么反馈；
- 哪些条件下生效，哪些情况下不处理；
- 是否有缺失界面、未覆盖需求或需要你决定的事项。

开工前，AI 先查找并核实必要的预制体、协议、配置和需求描述；缺项或歧义集中列出，整个需求停止实施。材料齐备后按功能展示使用依据，经你确认才开始编码；确实不涉及的协议或配置会说明理由。隐藏或无法截图定位的交互仍保留文字说明，未实现与未验证内容如实列出。最终取得你对当前交付的实际验收后才封存；返修后更新展示，旧验收不能覆盖新内容。

| 入口 | 什么时候使用 |
|---|---|
| `$dloop` | 推进 Unity 长任务，不额外生成专门的 UI 截图标注计划 |
| `$dloop-ui` | 长任务包含界面修改，希望完成后集中验收完整交互与实际验证情况 |

### 需求怎样拆分

局部修改按普通 Codex 任务处理。需要 DLoop 管理的长任务按可分别验收的业务结果组织切片，同一结果所需的代码、配置与验证通常一起完成。计划说明场景由谁承接、依赖什么、怎样验收；共同接口与数据责任先统一，关键未知先调查。实施中只重新核对受影响部分，最后仍从完整需求核对业务流程。已有材料够用时不增加文档、评分或确认轮次。

不清楚预制体位置时，提供需求或界面名称与项目位置即可由 AI 查找。找不到时说明已查位置、影响和需要补充的内容，补齐后再确认开工；不会以计划新增或占位资产绕过必要材料检查。

### 继续、调整或暂停

回到项目后，直接说清功能名称和意图：

```text
$dloop
继续“<功能名称>”任务，从当前进度往下推进。
```

```text
先暂停“<功能名称>”，保留当前成果。我需要调整需求。
```

工作流根据已保存的进度处理。涉及 UI 方案的任务继续使用 `$dloop-ui`；你也可以直接指出需要调整的行为，由工作流整理影响并重新呈现需要确认的部分。

## 审核时，你会看到什么

文档按业务场景组织，帮助你快速对照预期。例如下面是**内容形式示例**：

> **场景：一次用户操作**
>
> **操作与效果：** 说明操作入口、执行条件和用户能够观察到的变化。
>
> **关键约定：** 说明应当保留的现有行为，以及条件不满足时怎样处理。
>
> **请你确认：** 以上操作、结果和边界是否符合预期？
>
> **界面定位：** 涉及 UI 的任务附真实截图与修改标注。

确认前看目标、效果和取舍；交付时沿相同场景查看实际结果、偏差和未验证部分。详细设计、评审和验证记录仍可继续查阅。

```text
你给出需求
    ↓
整理需求（普通 DLoop 确认需求；DLoopUI 内部整理）
    ↓
调查项目、形成设计与计划；关键取舍按需确认
    ↓
分步实施 → 独立评审 → 返修与验证
    ↓
查看交付结果与需求差异；DLoopUI 集中人工验收
```

普通 DLoop 完成交付验证后自动封存，最终人工验收按需进行；DLoopUI 须取得当前交付的人工验收后封存。影响预期的新变化仍需你判断。
