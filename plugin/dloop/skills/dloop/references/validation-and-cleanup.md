# 验证、冻结与清理

DloopUI 特例：四类必要材料与开工确认必须持续有效，缺项或依据变化时停止实施并重新核对。需求与设计保持内部材料，最终展示场景验收导航，取得用户对当前产品结果的验收后才封存；游戏内验收的同一次回复即可登记，不能沿用普通 DLoop 自动冻结规则。

## 进入验证

确认需求、设计和计划已刷新且无阻塞，运行交付档案全局结构校验与索引重建，再由生命周期门禁进入验证中。这里的全局校验只检查交付档案，不代表运行项目代码全量。门禁失败按返回阻塞项修正，不手工改写状态。

最终验收前检查验证入口及明确选择的必要材料。交付必须至少有一个已接受实现候选，全部切片已经收敛，每个已接受候选都具备身份独立、结论通过且摘要匹配的评审，并依据同次投递的唯一验证策略核对最终工作区和剩余风险。实施与验证总览不能替代实现候选；没有实现切片的事项退出 DLoop，按普通任务处理。

全局修改占用释放后，工作区仍必须保持在最后一个已接受候选的完整防护摘要。下一切片取得修改占用前和最终批准前都重新检查该摘要；切片间或最后评审后的未绑定变化直接阻断，不得吸收到新切片基线或最终批准快照。

验证入口记录实际验证证据、结论、覆盖范围、未验证边界和残留风险。只有用户实际作出最终业务验收决定时才记录阶段决定；交付不等待例行人工验收。所有动作仍受常驻入口安全边界约束。

## 按已确认场景展示验收

验证入口复用已批准需求中的场景名称并链接对应正文，逐个对应实际结果，不复制需求形成第二份规格，也不按控件状态重新拆分。开头先显示本次变化、实际偏差、未验证部分和仍需人工判断的事项；影响批准的边界不得折叠到过程附件中。无变化的调查、检查点和评审经过只保留追溯入口。

逐场景核对操作去向、应显示的信息和集合完整性，并沿状态变化核对触发到最终结果；例如三页签不能因其中两页通过就报告奖励预览全部完成，已收到更新能切页不能证明到期会请求更新。对照源数据证明本人、列表及不同排序结果的含义没有混用。证据覆盖不到时明确未验证，不用编译通过、字段存在或规划截图替代结果。

暂时隐藏、配置待补、后续切片承接的结果在验证入口直接列明影响和恢复条件。局部候选通过只代表其批准边界；整体结果仍缺已承诺内容时，继续完成或按既有流程明确调整范围，不改写需求迎合实现，也不把工具正常跳过当成业务结果完成。

每个场景按实际需要给出可定位的体验入口、必要初始配置、简短操作、实际结果及证据。Unity 使用真实场景、菜单或运行入口；界面差异优先同条件截图，时序用实际录像，手感提供可体验内容，纯规则用输入和数据前后变化。已有入口够用时不新建演示场景，不强制每项都有截图、录像或试玩包。缺少可运行环境、入口或证据时明确该场景的未验证部分，不能生成假入口或把示意、规划截图与原型当成最终结果。

可重复的细节与关键分支由适当测试验证，附可复核结果；需要人判断的布局、手感与业务取舍明确保留。技术检查通过不代替人的业务批准。沿用 Prefab 的能力仍需验证当前场景中相关的接线、遮挡、输入与状态清理等实际集成影响，不要求人体验所有内部状态。

交付结果偏离已确认需求时直接展示偏差及影响，不能把需求改写成实际结果掩盖差异；涉及范围调整时按已有需求变更与批准流程处理。场景展示是现有验证正文的组织方式，不新增场景状态机、审批点、数量门槛或机器完成证明。

## 验收材料交接

验证入口集中维护“后续接入清单”：影响的功能或场景、所需输入或待完成内容、提供方或承接任务、接入位置、补齐后的验证方式、当前状态。没有缺项写无，不编造负责人或交期；未确认提供方明确写待确认。沿用原场景与证据链接，不把缺项拆成第二套工作流。后续同版本阶段直接引用这一节，承接后在原清单记录去向；范围外事项保持明确延期。

汇报接受情况时读取 `workflow-status` 返回的 `delivery_view.delivery_summary`，并结合验证正文说明验证程度。已接受、证据有未验证边界、档案尚未冻结可以同时成立；`feature.json` 的冻结验证字段仍待填不代表用户未接受。冻结按下文交付条件自动执行，不得为了改善显示补批准或把未运行写为通过。源码文字断言只能证明所检结构，不能凭检查数量声称点击、时间流逝、渲染或释放已实测。

进入最终验收前，验证入口必须完整记录实际证据、未验证边界和残留风险。最终验收角色视图从正式材料和不可变评审快照一次投影已批准需求与验收条件、验证入口、全部已接受候选及对应独立评审，并校验一次性提供的集成确认文件定位。任务消息不复制这些事实，也不新增交接文件或状态；最终验收者按评审模块中的输入合同独立核对。

验证决策保持单线。项目现有测试运行器已经提供相互隔离的分片、独立运行环境和统一结果收集时，可以并行运行互不依赖的只读检查；统一构建、资源准备、覆盖最后变化的集成验证、业务验收和结论写入仍由单一上下文完成。测试分片发生资源争用、相互影响或结果不可单独归因时立即改为顺序执行。

## 最终验证

最终验证固定并核对全部已接受候选、候选各自的批准方案绑定、摘要匹配且身份独立的评审集合，以及覆盖最后变化的工作区与集成确认。确认文件使用候选集合摘要、包含 Git 或 SVN 当前修订的工作区防护摘要和自身文件摘要防止过期复用；它表达负责人的确认，不冒充测试执行记录。当前方案换版不能替换历史候选绑定；候选集合、评审集合、仓库修订、工作区变化或确认文件发生漂移时旧结果失效，修正完成后依据唯一验证策略重新判定受影响验证。内容未变化时最终业务验收和冻结直接复用。

本模块不重新定义验证等级或升级条件。计划、任务包、实施、返修和最终验证只消费唯一验证策略形成的等级与理由；没有新增风险事实时不得自行提高、降低或机械重跑。

## 失败处理

检查点只持久化通过、失败或未验证。产品断言、环境、超时和不稳定等原因写入说明，由负责人结合测试运行器原生结果决定修复、恢复环境、重跑或记录风险；系统不根据自由文本自动分类，也不强制固定重跑次数。候选提交前，契约登记的完整验证集合仍必须全部通过。

## 只读分享

用户要求导出分享材料时，对当前交付项运行 `export-share --feature-id <feature-id>`。命令只从规范档案生成只读快照；快照不包含机器工作流状态，不能作为正式工作流输入。发布前来源状态发生变化时放弃本次结果，不自动重试，调用者按最新状态重新显式导出。

## 冻结

冻结表示本轮开发交付记录已封存，与用户是否验收分别记录；不锁定项目代码，不新增解冻入口。用户后续自行 debug 或让普通 Agent 修复无需解冻、无需重新走 DLoop，冻结记录只描述当时交付；需要 DLoop 管理新的交付时另建交付项。

当前批准方案的全部切片收敛且至少一个实现候选独立评审通过后，协调者主动进入整体验证，不再询问是否开始例行收尾。先反查已批准需求是否全部承接，完成必要集成验证与现有独立最终评审；切片数量完成不能代替整体结果完整。缺少已承诺结果、必要验证失败或仍需决定范围和风险时，处理具体阻断，不宣布交付完成。

六类文档须完整、新鲜、无草稿或阻塞，验证结论通过，未验证边界和残留风险明确为无或已记录。交付评审结论就近记录在验证入口；不新增评审账本或人工批准。明确记录实际结果、体验入口、后续接入清单和人工验收状态，无回复时保持尚未验收。普通 DLoop 默认不等待用户说“验收通过”或“冻结”；用户明确要求先验收、暂停或已退回当前结果时，先按其指示处理。

材料就绪后用 `transition-lifecycle --feature-id <id> --to frozen --integration-confirmation <文件>` 提交实际验证结论和边界状态。工具核对需求及适用的架构批准与 DloopUI 最终交互验收、全部计划切片、独立评审、工作区和当前集成确认；已有有效最终批准时可复用其集成确认。普通 DLoop 缺少最终人工批准不阻断冻结；DloopUI 必须有有效的最终人工验收，冻结也不写入或改成人工批准。确认或工作区变化时补齐受影响验证，不因冻结机械重跑。

冻结成功后，SVN 项目整理提交组，Git 项目跳过归组并保留暂存区，再向用户报告本轮已交付并封存、人工验收状态、实际验证范围与后续 debug 入口。SVN 归组失败如实报告未完成的整理；不宣称已提交版本库。冻结失败保留可写档案，处理工具返回的具体阻断，不无限重试。

## 保留期与清理

保留期检测只标记到期待清理，不删除。查看或重建索引不能替代清理。

清理必须：

1. 对明确交付项运行预览；
2. 检查删除目标和全部拒绝原因；
3. 只有用户明确要求执行且预览允许时才追加执行参数。

不得把执行清理与读取、校验、索引重建或保留期检测隐式组合。多个目标必须全有或全无；冻结验证、保留理由、文档状态、引用或目录安全任一不满足就拒绝。

## 完成验证

全部实现集成后依据唯一验证策略核对最终变化并补足必要验证，随后运行档案校验、索引重建，确认当前刷新队列为空，并把实际变化与验证结果分别记录到实施和验证入口。

## 交付提交组

SVN 项目在收尾文档、索引、验收状态或分享快照产出后运行 `sync-svn-changelist --feature-id <id>`，确保同一交付项的全部正式产物都在同组；新增产品文件应在最终检查点前纳管。归组失败不能报告交付已整理完成。只读候选评审和最终验收角色不执行整理，由主协调者完成。报告返回的组名、文件清单、目录操作、混合原有修改及未完成项，并说明未实际提交 SVN；服务器提交仍需用户明确授权。Git 项目跳过本节，不以暂存或提交作为封存条件。
