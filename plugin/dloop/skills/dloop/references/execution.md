# 实施切片执行闭环

DloopUI 特例：需求和设计仍是内部材料；调查后核实预制体、协议、配置和需求描述，全部必要输入齐备并取得用户对当前开工清单的明确确认后才能实施。缺项、歧义或确认失效时停止整个需求的实施，只继续调查和整理材料。更换业务依据后重新确认，内部实现或截图补充不重复确认。最终通过统一 HTML 展示并取得用户验收后才封存。

本文件定义实施切片、契约门禁、实施熔断、持久执行身份、修改租约和独立候选评审规则。

DloopUI 每个实施单元都要核对相关后端、已有代码和实际界面，补齐原范围内有依据的交互，并同步设计和验证材料。候选评审必须从原需求查实现、从实际实现查交互说明；内部草稿遗漏不阻断实施。缺少业务事实、冲突或超出授权范围时交还协调者处理具体问题。最终展示与验收遵循 `ui-interaction-review` 规则。

## 单线角色合同

- 实施、候选验收、返修和候选处置依次单线交接，不在本阶段发起并行调查或并行实现。
- 实施者和评审者不读取常驻入口。主协调者创建下游上下文前使用 `prepare-handoff --action implementation --role implementation|review` 检查并装配材料，通过后主协调者只传递当前交付项、角色和必需执行身份组成的最小任务消息，以及工具生成的读取命令。执行身份由已启动切片或未使用的评审身份建议取得，准备不预占身份。当前角色在自己的上下文中使用 `context-summary` 从正式材料一次投影设计、任务包、候选、验证或返修事实并独立核对。
- 角色视图全有或全无。输入缺失、陈旧、冲突、棒次不匹配、审批失效、身份非法、自评或候选漂移时，原样返回稳定阻断并停止；视图形成后仍缺业务决定时报告具体缺项。任务包引用是调查起点，实施和评审可只读核对当前调用链、相关实现与项目惯例，不把引用清单当作只读白名单；产品修改仍限于授权写入范围。
- 实施者按角色视图核对目标、材料、写入范围、验收、验证和停止条件，只在授权范围修改；最终检查点覆盖登记验证并通过后，用 `submit-slice` 提交待检查结果。命令先装配评审材料，通过后才固定候选并交还协调者；缺项时保留原执行身份，在原上下文补齐并重新提交，涉及代码变化时按既有策略更新检查点。
- 评审身份必须不同于实施身份。评审者只读完整任务包、任务包引用的批准设计、固定候选和工作区实际变化，不得使用实施对话，不得修改候选或工作区。角色视图直接投递真实流程正确性、项目惯例、设计偏差与维护成本的判断规则；批准设计有误时明确退回，不以符合方案代替正确性。拒绝未批准的公共接口、跨模块职责或状态归属、外部配置合同和恢复协议变化；授权范围内保持已批准外部行为与安全约束的内部整理不因缺少单独架构批准而退回，仍检查正确性和维护成本。提交结论后停止。
- 返修者使用新的执行身份，从不可变评审快照和正式返修交接取得原候选、完整问题集、允许范围及保守重验范围。范围或契约边界变化时停止返修，转入熔断或新切片。
- 任务包、切片方案、检查点和候选先使用 `prepare-action-input` 生成当前字段合同，不读取历史示例或手写字段集合。按返回的 `input_guidance` 填写嵌套对象，使用 `target` 编辑、`next_action` 执行后续检查；示例不是业务事实。生成器不覆盖已有文件；确定性失败只修正报告的缺项，输入没有变化时不重试。
- DloopUI 任务还须按验收场景声明 `delivery_requirements`，候选通过 `delivery_materials` 交回实际文件；同范围遗漏追加 `additional_delivery_requirements`。独立评审直接读取交接文件，最终由统一模板入口汇总，材料返修只更新受影响引用。字段遵循 DloopUI 材料交接合同，不靠角色对话传递材料。
- 正常批准、启动、提交和返修由执行操作在事务内核对资格。机器只在正式事实唯一时给出下一机械动作；范围、方案、风险接受和候选处置交由主协调者决定。

交接准备默认返回 `handoff_ready`、最小任务消息与下游读取命令，缺项时返回来源与补齐责任；仅排查时使用 `--include-role-view` 展开完整角色材料。两种模式执行相同检查，不缓存准备结果；阻断时不返回部分可执行合同。`start-slice` 和返修启动先检查材料再切换身份与租约，成功返回已装配材料；协调者随后准备目标角色的完整合同，材料就绪后才创建下游上下文。原上游负责自己有权修改的缺项，需求、设计或批准问题交还协调者；程序只装配已有事实，不补造测试、业务决定或评审结论。准备结果即时派生，不保存新的交接档案或就绪状态，不启动模型、不自动重试；下游继续使用同一材料规则独立核对。

## 任务包与切片契约

写入范围只填写项目相对的具体文件或目录，目录包含其子项；不支持星号、问号或方括号通配表达。生成代码与对应元文件也须被范围覆盖。DLoop 自有档案作为上下文材料引用，不放入产品写入范围；正式阶段文档按协调者的写入目标维护。

使用代码或绑定生成器时，开工前先运行项目已有的只读预检查，将预计写入的文件填入任务包 `generated_write_scope`，包括目标预制体的绑定信息、生成代码、缺失时创建的逻辑和新增元文件。工具检查全部路径已被 `write_scope` 覆盖；不通过时在开工前补齐范围。没有生成操作时留空。生成器未提供完整清单时核对其实际保存位置；“不改变视觉”不代表“不写预制体”。实施前再次核对目标和配置未改变，不自行推测生成器不存在的预检查能力。

原范围外变化未解除时，重试返回具体文件和当前生效契约版本，不启动新执行、不消耗新身份。修改任务文件不改变生效范围，重新执行也不会重置原基线。先保留成果，按返回原因恢复越界变化；需要改变范围时交还协调者，按快照规则选择并预览恢复起点后重新登记契约。新增范围的既有改动必须保留完整差异供评审，不能通过重试把它们当作干净基线。本版不提供保留全部越界成果并自动修订范围的入口。

任务包声明标识、写入范围、必要上下文材料，以及 `slice_contract` 与 `contract_check`。目标、非目标、验收条件、验证和回滚只在切片契约中声明一次，工具校验后为角色视图和既有执行消费者生成只读投影；输入不得再手工复制这些字段。切片契约必须同时声明 `validation_level` 和 `validation_rationale`，使实施者、返修者和协调者看到同一个测试层级及升级理由。材料必须使用 `context_contract_version: 2`，每项包含 `source`、`purpose` 和互斥读取模式：

- `mode: sections` 必须提供非空且不重复的 `sections` 标题列表；
- `mode: full` 必须省略 `sections`。

合同版本缺失、版本不匹配、字符串材料或未知字段直接失败。章节按精确 Markdown 标题读取，缺失或重复时返回精确输入缺失，不回退整份读取。

切片契约正文必须完整声明业务结果、非空且不重复的可观察验收场景、范围内四类责任、范围外、依赖假设、预计影响区域、不变量、验证方式、未知项、回退点、切片特有熔断条件、决策负责人、批准状态、版本和修订摘要。任务包中的目标、非目标、验收、验证和回退必须与契约对应字段一致。预计影响区域用于暴露预期闭环，不是文件白名单。

可观察验收场景沿用已批准需求的业务名称和材料定位，再补足本切片需要的验证；展示场景与实现切片不要求一一对应，不为拆分控件状态增加切片。实施中保留与场景有关的真实结果和已有体验入口，供最终验收直接引用。

任务包引用本切片相关需求场景及必要的原始来源定位；交接自动补入未引用的需求入口和设计入口，已有精确章节选择仍保留。实施者与评审者核对原意、设计和实际结果，不只核对方案自洽。信息展示的验收落到对象、位置和真实数据；状态切换覆盖触发、获取新事实、回包更新与条件未满足时不切换。缺少场景或来源时由协调者补齐，不能按现有组件猜业务含义。

切片缩小范围时，把暂未实现的业务结果交回计划，注明承接切片或依赖输入、影响与恢复条件；不要求当前切片越界完成其他切片，也不把“本切片非目标”解释为整体需求取消。依赖补齐时重新核对所有受影响结果，例如奖励配置接入同时影响奖励预览页签、宝箱和状态刷新，不能只验证配置可读。改变已批准外部结果仍走现有变更流程。

`contract_check` 对独立验收、强依赖可用、结构性未知项、影响闭环、用户可观察验收、回归保护和安全回退逐项给出布尔结论与证据。工具还会核对强依赖与结构性未知项的契约事实以及人工批准状态。失败结果保留原因；能在当前切片内补全的修改契约，结构性未知先调查，需要前置、替代或重新划分时修改方案并创建新切片。检查失败不取得修改租约。用 `prepare-slice-contract` 记录草稿，用 `check-slice-contract` 形成可审查结论；`start-slice` 会再次执行同一门禁。

尚未开始实施的草稿、检查失败或已就绪切片确定不再使用时，先调用 `resolve-slice --feature-id <feature-id> --action release --package-id <id> --workspace-decision kept` 将其标为放弃，再修改方案并创建新切片。工具保留原契约与检查历史，不改动工作区或其他切片的修改租约；新方案可以移除这条未实施的声明。已经进入实施的切片仍按下文的异常或熔断收敛规则处理。

新任务包先生成严格输入，再填写事实：

```powershell
python Tools/FeatureArchive/feature_archive.py prepare-action-input `
  --feature-id <feature-id> `
  --input-kind task-package `
  --package-id <package-id>
```

任务包登记后，统一交付视图通过任务包标识直接给出契约检查和启动参数，不再要求重复传入任务包文件。新执行身份从同一下一动作合同取得；调用方不得另行猜测或预占。

契约版本只增不减。同版本只允许重新提交检查证据，任务包或契约正文变化必须提升版本并记录修订摘要；历史版本不覆盖，已通过契约不会被同版本草拟动作降级。实施中的验证加强只通过唯一验证策略规定的补充入口进行，不能重交任务包扩展业务授权。检查点输入中的契约版本由生成器填写，登记时必须与当前契约一致；旧输入不能原样重交。

## 版本化切片方案

协调者把计划阶段已经核对的结果边界转为切片声明，不能把编码、配置和测试步骤机械各建一个切片。登记前核对计划正文中的场景承接、共同依赖和验收依据；只有关系图合法不能证明拆分合理。缺少拆分依据时回到 `plan` 动作补齐，机器声明继续只使用现有字段合同。

首次实施前及切片发生合并、替代、范围或依赖调整后，在现有计划中复查受影响场景的归属、依赖顺序和整体结果；按原有文档确认、方案换版及熔断规则处理。已接受候选保留历史绑定，未受影响部分沿用，普通范围内测试失败不触发重新拆分。后续切片临近启动时补齐契约并通过既有检查，不把尚未细化当作放弃原需求。

- 用 `prepare-action-input --feature-id <feature-id> --input-kind slice-plan` 准备规范计划目录中的草稿；首版填写至少一个实现切片，换版基于当前批准方案调整。再次准备返回同一草稿，不覆盖编辑或增加版本。角色材料的 `input_preparations` 返回同一入口。
- 实施前由协调者使用 `check-slice-plan` 检查与交付项同标识的方案声明，再使用检查结果中的摘要调用 `approve-slice-plan`。批准入口在同一事务内重新规范化和检查，拒绝摘要漂移、同版改写、降版和破坏既有实施事实的换版。
- 至少一个切片执行完整关系合法性检查，并返回带类型有向图、非法关系链和从当前切片状态重算的实时资格；图和资格只即时派生，不写入第二份状态。
- 前置边从前置切片指向等待切片；替代边从替代切片指向被替代切片。图只计算资格，不执行启动、恢复、批准或验收。
- `start-slice` 只启动当前批准方案内且资格满足的切片；无当前批准方案、目标不在方案内或资格不足时直接拒绝，不隐式建立或扩展方案。
- 首次启动保存完整批准历史绑定，原范围重试继续使用同一绑定。候选把方案版本、摘要和不可变批准历史引用纳入自身固定事实与摘要；提交结果和独立评审上下文返回同一绑定并可复核完整声明，方案升级不改变历史候选。
- 状态校验对每份批准历史重新执行完整声明与大切片图语义检查，不能通过同步改写摘要绕过非法关系检测。

发生可明确说明的格式试错、重复查找或交接退回等额外劳动时，在本轮自然收尾处使用角色视图的 `friction_note` 入口补记；已有异常则关联返回的问题身份。恢复后可补一句关键改动与已知代价，不为记录另开上下文。记录只写旁路日志，候选评审对产品和正式业务材料仍保持只读；操作恢复不代表工作流根因修复，记录缺项不阻断交付。详细参数仅在需要时读取 [摩擦记录说明](friction-records.md)。

## 实施检查点与熔断

### 验证策略与评审补充

代码与宿主验证强度只使用同次投递的唯一验证策略。任务包记录该策略形成的等级、理由和验证集合；实施与返修沿用同一结论，实际变化或失败证据产生新风险时停止并交回主协调者重新判定，不在本模块维护第二套升级条件。

独立评审者核对需求与批准设计，并按实际风险决定是否补充负向或边界测试。评审验证证据和不适用理由都是可选补充，不进入候选集合摘要，也不作为通过结论的格式门槛。

- **评审快照**是一次固定候选与一次独立评审结论组成的不可变记录。返修产生新候选和新快照，旧快照保留；创建快照本身不运行外部测试。
- **集成确认**是负责人对当前集成结果的确认文件，绑定全部已接受候选集合摘要和包含 Git 或 SVN 当前修订的最终工作区防护摘要。三个内容均未变化时，最终验收和冻结复用它；确认文件本身不证明测试命令已经执行。

实施者只在完成验收场景、改变关键数据流、引入依赖、首次验证失败或准备修复上一轮失败等有意义节点使用 `checkpoint-slice`，记录本轮假设、改动摘要、新发现、下一步，并提交本轮实际运行的已登记验证。先以 `prepare-action-input --input-kind checkpoint --execution-id <execution-id>` 生成与当前契约验证集合一致的输入；输入不含检查点标识，成功记录后由工具按当前执行顺序生成。中间检查点允许验证子集；候选提交前的最后检查点必须覆盖契约登记的完整验证集合并全部通过。验证状态只有通过、失败或未验证；环境、超时和不稳定等原因写在说明中供人工判断，不据此自动重跑或自动熔断。

以下事实一经明确命中立即熔断：业务结果或验收实质变化、范围外成为必需项、强依赖失效、必须改变公共或存量数据、必须破坏不变量、无法独立验收、安全回退失效，以及契约声明的特有条件。负责人提交规则、失效假设和证据；工具自行推导是否越界及命中规则，不接收单独的越界布尔值。

不使用百分比、工作量估算、固定失败次数、失败方法集合或人工“无改善”信号自动熔断。普通测试失败继续由实施 AI 在批准目标内诊断、修复和重跑；只有契约边界明确失效或工作区实际出现授权范围外变化时才单次熔断。

熔断报告由工具根据检查点、验证和工作区事实生成，包含触发规则、失效假设、已完成与未完成验证、可安全保留证据和发现，并固定声明两种收敛动作。状态进入 `circuit_open` 后，后续检查点被拒绝，工作区成果与全部历史保留，工具不自动回退。

## 熔断收敛

熔断后只允许通过 `resolve-slice` 二选一收敛：

- 选择 `retry`，提供新的执行身份，在原任务包、原契约、原批准方案绑定和原写入范围内继续修复；
- 选择 `release` 前由人工把授权范围和版本管理工作区恢复到执行基线。工具实测一致后只终止当前切片并释放租约，不执行恢复或删除成果。

熔断揭示需要前置、替代、扩大范围或重新划分时，不修改原切片的关系、契约或恢复状态。主协调者先终止原切片，再修改版本化方案并创建新切片；新切片按普通契约检查、启动、候选和评审流程推进。

## 执行事务

1. 主协调者依据已批准且新鲜的需求、设计和计划形成任务包、切片契约与七项检查；改变独立模块职责、公共接口、跨模块状态、安全或回滚合同的切片引用已通过独立设计评审的材料。
2. `start-slice` 在契约与方案资格通过后，从当前项目的 Git 或 SVN 工作区取得全工作流唯一修改租约。相同执行身份、任务包和工作区的响应丢失可安全重试；不同输入或活动身份冲突由工具拒绝。
3. 实施者从角色视图开始，在范围内修改并记录有意义的检查点。普通失败继续诊断；边界失效形成熔断报告并停止。全部登记验证通过且工作区未漂移后提交候选。
4. 主协调者先准备候选评审交接，通过后创建身份独立的新评审上下文。评审者只读核对目标、批准设计、实际变化和验证结果，提交通过、失败或未验证结论；失败后只在已批准范围返修，边界问题回到熔断。
5. 通过后释放租约。至少一个切片形成已接受候选且全部切片收敛后，主协调者按唯一验证策略核对最终工作区与风险，形成集成确认；最终验收只核对并复用未过期确认。没有实现切片的事项不能进入最终验收，应退出 DLoop 按普通任务处理。

## 统一交付视图

指定交付项的 `workflow-status` 与协调者的 `context-summary` 共享同一只读 `delivery_view`。视图从现有档案、执行账本和当前工作区即时派生，不写入第二份状态；它给出当前阶段、是否可推进、结构化阻断、唯一下一动作或人工判断点，以及需求、架构、最终批准、切片评审和当前候选摘要。下游仍经过相同完整检查，但交付视图仅返回当前阶段和阻断；当前任务包、候选、评审、集成确认与必要复核随对应角色合同完整提供，不补读全局进度或其他切片历史。实施写入范围只读取任务包中的 `write_scope`。

状态查询默认只返回这份交付视图，不在顶层重复展开批准、切片、方案或修改占用。全局查询只返回占用身份，不投递恢复正文。只有需要排查历史、完整检查结果或基线时，协调者使用 `workflow-status --include-details` 取得明细；展开与默认查询执行相同检查，不改变恢复、批准或释放权限。

下一动作只有在现有事实唯一时才返回。至少一个切片已经验收且当前批准方案全部切片收敛后，工具给出进入整体验证的动作；协调者仍须核对整体需求覆盖，不要求用户重复确认例行收尾；没有已接受候选时明确要求继续形成实现切片，不提供进入验证的完成判断。独立评审和最终业务验收也不由机器替代。未封存档案的接手者必须刷新并检查 `required_rechecks` 中的三项结果：工作区是否偏离最后接受候选、最终验证绑定的候选集合是否仍等于当前集合、通过的评审身份与候选摘要是否仍有效。

## 人工回退

用户通过对话要求暂停、退回某阶段或推翻成果时，由主协调者先停止受影响的实施和后续交接，确认原执行者已停止写入，再读取当前状态。根据本轮与已有指示判断要重议的内容、保留的成果和撤销范围；信息已明确就执行，不要求用户编写命令或重复授权。只有保留还是撤销、或撤销目标确实无法判断时才追问，等待期间保持现场。回退理由、成果处置和下一步就近记录在原阶段材料。需要指定保存点或重做阶段时，按同批投递的中间态规则使用恢复入口，历史留在快照库。

- **暂停或保留代码重议**：保留当前文件、执行身份和修改租约，不提交 `interrupted`，因为该动作会恢复执行前基线。可以讨论方案；确认继续原范围后交还原执行者。需要正式更换契约或方案时，先按现有状态收口原切片；不能释放占用后把未验收成果当作已接受，也不能在未明确授权撤销时调用恢复动作。
- **原批准范围内改进实现**：活动实施交还原执行者修改；评审未通过的候选走原范围返修。实现偏离原批准行为时恢复原行为，不因此改写需求或增加人工批准。业务边界确实改变时才走既有变更或熔断流程，不能因用户不满意而编造契约失效证据。
- **明确撤销本轮实施**：仅当前状态为活动实施时，由原执行身份提交 `interrupted`，工具恢复本次执行开始前的授权范围基线并释放占用；这不是恢复到任意检查点或整个阶段开始前。原范围重做使用既有重试；确定不再使用原切片时将其放弃，再调整方案并创建新切片。失败、评审未通过或熔断等其他状态按下文既有收敛规则处理，熔断仍须先人工恢复基线。
- **待评审或已接受成果**：待评审候选保持固定，独立评审按实际问题形成结论，人工退回不冒充 AI 评审失败，也不故意改动候选制造漂移来绕过处置条件。已接受候选与评审历史保留；普通调整通过新变更切片处理，明确回退则使用保存点恢复并以新轮次继续，检查受影响依赖与验收。档案已冻结且用户明确要求继续由 DLoop 管理时，另建当前版本交付项，不重写冻结历史；普通 debug 按普通任务处理。当前状态没有符合意图的合法处置入口时，保留现场并说明具体限制，不手工改状态。

原执行收口后，按实际业务变化修改需求、设计或计划；没有实施占用时可直接处理文档。读取对应阶段与 `dependency-refresh` 规则，对实际修改材料确认语义变化，并刷新受影响下游。只有涉及人工决定时读取对应批准规则并如实记录；仍有效的批准复用，失效的按现有门禁重新确认。DloopUI 改变用户可观察交互时仍需复审。回退完成后说明保留或撤销了什么、哪些材料和批准需要更新，以及接下来从哪里继续，不机械重跑所有阶段。

## 异常与释放

首次出现沙箱辅助程序、访问控制、运行时缺失或等价权限基础设施失败时，立即停止并走既有中断与租约恢复路径；不得轮换探针、拆分等价命令、扩大批准前缀或重复请求用户批准。该分流不新增持久化权限状态、失败计数器、自动提权或后台监控。

任务或应用意外退出不会改变活动棒次。重新进入后先从 `workflow-status` 和角色视图确认原执行身份与唯一下一动作：结果明确时继续使用原身份提交；确认无法继续时显式提交 `interrupted`，由系统恢复执行前基线并释放租约。普通退出不推断完成、失败或中断。

执行中断、状态不明或熔断时保留现场并阻塞，不自动接管或跨状态补偿。熔断只允许原范围重试，或在人工恢复授权范围和版本管理全局基线后终止并释放。需要前置、替代或重新划分时修改方案并创建新切片，不为原切片增加等待或恢复状态。孤立租约只有用户明确授权且工作区恢复到授权范围和全局基线后才能释放。

## SVN 产物归组

本节仅适用于 SVN 项目。Git 项目跳过纳管与归组，不自动执行暂存、提交、推送或索引重置；实施前已有的暂存内容保留。Git 的检查点同时绑定暂存内容、工作目录内容与当前提交（无首次提交也可启动），无需为了检查点执行 `git add`。撤销本轮按授权范围恢复正文，不用 Git 整仓重置代替恢复。Git 授权范围跨入子模块或包含其父目录时，启动前拒绝，即使产物被忽略或尚未生成；子模块有变化时也停止，在子模块项目内独立运行工作流。

检查点通过前置合同和范围检查后自动整理 SVN 产物，依据当前切片实际差异和既有清单纳管新增文件，再固定工作区与候选。实施者也可运行 `sync-svn-changelist --feature-id <id>` 补同步。Unity 资源及父目录的 `.meta` 必须包含在授权范围与产物中。后续新增产品文件必须更新最终检查点；中断或放弃恢复正文后再次同步，取消被撤回新增文件的纳管以及已恢复文件的删除调度。失败保留成果，修复具体阻碍后重试，不能将失败记为完成。

分组是本地操作，不代表已提交服务器。已有修改保持原内容，在交付中注明混合文件；无关文件保留原提交组。目录不能加入 SVN 提交组，单独报告提交时需包含的目录操作。
