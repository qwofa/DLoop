# 需求、当前交付项与业务术语

版本交替后，`.scratch/dloop-history/` 内整批旧作业已归档失效，包含未完成作业；不继续执行旧任务消息，不使用旧批准或占用。需要沿用的业务内容作为新作业输入，在当前版本重新登记范围和验收。项目遗留代码改动作为当前实际起点，不视为已验收成果。

DloopUI 特例：需求和设计仍是内部材料；调查后核实预制体、协议、配置和需求描述，全部必要输入齐备并取得用户对当前开工清单的明确确认后才能实施。缺项、歧义或确认失效时停止整个需求的实施，只继续调查和整理材料。更换业务依据后重新确认，内部实现或截图补充不重复确认。最终通过统一 HTML 展示并取得用户验收后才封存。

## 开始或继续交付项

新交付项使用稳定小写英文标识和中文标题，并在独立的 `.scratch/dloop-v3/v3.9.1/outputs/` 根中使用唯一严格合同；普通 DLoop 初始化时省略配置参数；显式 UI 任务按 DloopUI 入口选择配置。旧根、旧合同、缺失合同或旧结构直接失败，不自动读取、补全或迁移。初始化后读取术语表和需求入口，维护精确依赖，校验档案并进入进行中。继续交付项时先读取持久工作流状态、执行只读审计，再读取术语表和当前动作入口。

需求入口独立记录目标、范围、非目标、验收条件和最重要边界。首次需要用户决策时一次性给出已确认事实、待决定问题、依赖、可逆边界和推荐方案包；只把会改变目标、外部合同、状态模型、高风险动作、数量级成本或最终验收的分叉交给用户。

拆分前先从已有材料明确使用者要完成的整体结果、必须成立的场景，以及会改变责任边界或实施顺序的未知项。场景明确但实现事实未知时交给调查，不要求用户先替 AI 拆任务；已有明确答案直接沿用。需求规模按结果能否独立验收、共同依赖和跨轮交接需要判断，不按字数、文件数或界面数评分，也不为了进入 DLoop 把局部修改扩大成长任务。

## SVN 提交组

先按当前项目识别 Git 或 SVN；Git 项目不要求安装 SVN，归组返回不适用是正常结果。Git 不自动暂存、提交或推送，已有暂存内容保留。

创建时从策划文档名称提炼简短中文业务主题作为交付标题；多份文档总结共同功能，不使用版本号或通用的“工作流产物”替代业务含义。SVN 项目初始化后运行 `sync-svn-changelist --feature-id <id>`，工具以标题和交付标识形成稳定组名，遇同名无关文件自动区分；非 SVN 项目返回不适用。组名确定后跨切片和恢复沿用。

文档、截图、正式输入、状态和分享材料使用规范产物路径。阶段产出完成后补同步；不能把整个工作副本的修改加入组。组名概括由协调者依据策划文档完成，不需要只为命名再次确认。

## 按业务场景确认需求

需求入口直接按人能够独立判断的业务场景组织正式事实，不另建摘要或原型规格。开头先说明当前问题、期望变化和本次待决定事项；影响批准的范围、代价、风险和非目标直接可见，细节按需放到后文或链接。再次提交先说明相对上次的变化，不重复铺陈过程。

一个场景说明主体、必要初始条件、关键操作和可观察结果，沿用业务名称以便计划和最终验收引用。只有不同结果可被分别接受或退回、关键业务边界在当前展示中不可见，或入口与初始条件显著不同时，才考虑拆分。取消、失败等分支可以在原场景中简短说明；不按界面、控件、Prefab 或视觉状态数量拆分，不规定场景数量和固定字段表。

从原始材料整理场景时，保留能复核业务含义的段落或图片定位；概括不能改变操作去向、信息对象或结果范围。相似页面和组件只提供实现候选，不能替代原意。复用现有组件时仍须保持原需求规定的操作去向；原文没有覆盖的同类入口也不能默认为已确认。确有歧义时说明影响，已有明确答案时直接沿用，不重复请求确认。

同一行为覆盖多个显示位置或触发条件时，在原场景内保留这些区别。多个入口或操作触发同一展示时，应分别说明更新、清除和不处理条件，不能只用一个总体完成结论覆盖这些差异。只展开影响本次结果的区别，不给所有控件新增状态矩阵。规划关联数和标注 PASS 只证明结构覆盖；评审仍回到原始来源核对具体位置、触发与不处理条件。

信息展示需要说清影响验收的对象和位置，不同对象、展示区域和判断条件所需的数据必须分别对应，不能用一个笼统完成结论替代。数据字段在调查和设计中核实，不在需求阶段猜测。依赖缺失造成的阶段性缺项保留在原场景中，写明缺少什么、影响哪些结果、谁提供输入以及补齐后恢复什么；暂不实现不等于从已批准范围删除。

根据尚需判断的问题选择材料：入口和信息用现状截图标注；操作衔接用分镜；布局和遮挡需要时用 Unity 预览；手感与时序需要实际体验时才做 Unity 最小可体验内容；纯规则或数据变化用具体输入与结果示例。已有材料够用时直接引用，不强制原型、媒体或前端模板。每个展示项都应帮助作出具体决定，不能只因控件存在某种状态就生成。标明现状、设计示意或待实现原型，不把它们作为最终实现证据。展示制作服从当前阶段与授权范围，不因需要体验而提前实施未批准的完整功能；暂不能制作时明确待判断内容。

Unity 中未被需求改变的现有表现默认沿用。沿用说明只引用已定位的资产或项目惯例，不枚举按下、回弹、长按和过渡等封装状态。只有需求改变交互，或交互影响业务结果时才调查相关能力；截图不能证明行为。依据不足时记录具体待核实项，不推定能力，也不扫描全部组件补一套状态矩阵。沿用不免除后续集成验证，且不等于整个场景无需接线或产品修改。

批量操作应在同一场景说明确认后的数据变化、受保护对象的处理以及取消后的数据保持。沿用按钮回弹不成为展示项。若本次就是修改长按确认的触发时机，则展示相关时序与取消边界，不能以沿用为由略过。

## 术语表

- 每个交付项都保留 `01-requirements/terminology.md` 作为结构必需文件。术语正文按需维护，没有候选术语时保持明确的空状态，不为填充结构制造无歧义术语。
- 术语只锚定一个稳定业务概念或职责，保存首选术语、一句话定义、确有混淆时的相邻边界、真实别名和候选或已确认状态。
- 状态组合、触发条件、实现方案和验证规则分别放回需求、设计或验证，不塞入定义。
- AI 在需求讨论中静默发现候选。只有同一表达存在两种会改变范围或职责的合理理解时才列入；普通代码标识、节点、字段和无歧义自然语言不收录。
- 候选在第一次需求共识中批量确认，不新增常规确认点。

已确认术语在交付正文中使用指向当前术语表的粗体 Markdown 链接；候选术语不能正式引用。普通文档链接只导航，不自动产生语义依赖。

## 术语变更

- 无语义改名使用 `rename-term`，不要跨文档文本替换。
- 定义变化前可运行 `analyze-impact`；编辑术语表后以语义变化确认。
- 工具使直接依赖过期。按 `refresh-queue` 逐层处理：中间层含义不变时以非语义变化确认并停止传播；含义变化时改正文并以语义变化确认。
- 队列清空并通过 `assert-fresh` 后才能使用下游材料。
- 冻结和待清理档案不刷新；历史术语只能作为新交付项候选，不建立实时共享引用。
