# 评审、批准与独立冷读

## 适用边界

本模块只适用于需求共识、按需重大架构确认、最终业务验收和独立冷读。候选实现验收属于复杂配置的实施切片闭环，集成验证属于验证环节，均不使用本模块代替。

实际发生因材料缺项或歧义导致的退回、重复查找或转述时，当事角色使用角色视图的 `friction_note` 入口就近留简短说明；恢复后可补关键改动与已知代价。该入口只追加旁路日志，不改变只读评审、正式结论与候选；正常讨论和必要评审不自动算摩擦，补记不成为交付门禁。需要时读取 [摩擦记录说明](friction-records.md)。

## 人工确认

普通 DLoop 的常规人工确认保留需求共识；最终业务验收仅在用户实际作出决定或明确要求先验收时进行，不作为开发交付自动冻结的前置。重大架构高杠杆分叉可按需增加一次架构确认；调查、计划、普通实施和修复不增加确认点。只有用户明确批准或退回后才能记录阶段决定，不能从沉默、测试通过或旧批准推断。

显式 `$dloop-ui` 使用后置集中验收：需求与设计只检查内部材料就绪，不要求例行人工批准，也不把内部就绪登记成人工决定。实施中补齐原范围内有依据的交互，只有缺业务事实、冲突或超范围才提出具体问题；用户主动要求先审方案时遵从。

### DloopUI 最终交互验收

实施候选接受后，从原始需求核对实现、从实际实现核对交互说明，使用 `ui-publish` 提交完整交互与双向核对证据。所有页面由内置标准模板生成；先打开 `06-validation/ui-delivery.html` 验证显示和定位，再交给用户集中验收。隐藏目标仍保留条件、操作和结果，未实现与未验证内容如实列出。

交付视图 `ui-delivery.review` 提供展示材料和当前 `reviewed_digest`。用户实际回复后才调用 `stage-action --stage final`，传入 `--reviewed-digest` 和 `--user-confirmation`（用户回复定位与原文）；批准还需当前集成确认。摘要不一致、实现候选改变或必要验证未完成时先更新材料。未回复不自动批准或冻结，不建立逐交互批准账本。

## 独立设计评审

创建设计评审上下文前，主协调者在原上下文调用 `prepare-handoff --action design --role design-review`。缺少正式设计内容或材料陈旧时先补齐、确认和刷新；返回 `handoff_ready: true` 后才发起独立评审。只交付返回的最小任务消息与读取命令，不交付作者对话或预期评审结论。

新增、拆分或合并承担独立职责的模块，改变公共接口、跨模块职责或状态所有权、权限或数据安全、回滚合同，或者引入改变外部可观察行为的配置、错误模式和执行顺序时，必须在实施前复用重大架构确认完成一次独立设计评审。授权写入范围内，保持已批准外部可观察行为、公共接口、跨模块状态归属和安全约束的内部整理，由实施者决定并接受候选评审；私有辅助逻辑、等价校验顺序和错误处理收拢不单独触发架构评审或人工确认，也不因此获得范围扩展或任意重命名权限。评审者读取已批准需求和设计入口；从设计材料出发只读核对能够改变判断的相关调用链、已有实现与项目惯例，不把材料引用当作只读调查白名单，存在明显简化空间时再比较更简单替代方案，不得只根据设计文档是否自洽给出结论。

设计入口必须已确认并包含可评审的设计内容，但不强制固定标题；项目核对路径和更简单替代方案按实际需要记录。主协调者使用未参与方案编写的新原生子 Agent 单线发起评审，任务消息只交付当前交付项和设计评审角色。评审者通过 `context-summary --action design --role design-review` 自行取得完整角色合同、正式材料路径和停止条件；设计入口仍为空或保留待补充占位时，角色视图只返回设计内容缺项并停止，不修改档案或实现，不替主协调者裁决范围。主协调者等待最终返回后串行处理结论。

设计评审检查调用方为了正确使用模块必须了解的规则、复杂度是否隐藏在模块内部、删除模块后复杂度是消失还是分散回调用方、是否为单一实现建立假设 seam，以及新增状态、版本、错误分类和恢复规则是否有真实消费者。评审返回设计偏差、残留风险和通过、退回或未验证结论；发现有价值的简化方案时一并返回。主协调者负责裁决并串行修改正式设计。未通过或未验证时不得进入实施。

## 独立冷读

创建冷读上下文前，主协调者用 `prepare-handoff --action <当前动作> --role cold-read --entry-question <问题> --allowed-material <正式材料>` 检查并装配，材料参数可以重复。入口问题和允许材料缺项在原上下文补齐，就绪后才发起冷读；预期答案与事后比较用的必要事实不作为准备输入，也不传给冷读者。下游继续独立读取和判断。

独立冷读只验证正式材料能否被没有前序上下文的读者准确理解，不判断模块设计选择是否合理，也不验证实际实现。实施完成后不增加冷读；模块设计质量由实施前的独立设计评审检查，实际实现与批准设计的一致性由候选验收检查。

冷读者不读取常驻入口。主协调者按冷读输出合同交付当前交付项、冷读角色和入口问题，并在当次 `context-summary` 调用中提交允许材料；冷读者按输入合同自行取得并核对完整流程合同、允许与禁止操作、前置门禁、精确正式材料引用、输出和结束条件。临时输入不写入档案。角色视图全有或全无：入口问题或允许材料缺失、材料陈旧或冲突、当前存在尚未闭环的实施、评审或返修棒次、审批状态不适用时，原样返回稳定阻断和回到主协调者的下一机械动作，不输出部分可执行合同。

冷读只使用原生子 Agent 单线交接，主协调者等待其最终返回。不得通过 Windows 命令行、管道或外部 Codex 进程模拟独立冷读。原生交接失败时只返回未验证并交还主协调者，不得形成需求结论；需要重试时新建原生冷读上下文，并继续保持单线。

独立冷读只复用需求共识、按需重大架构确认和最终业务验收时机。主协调者临时声明入口、允许读取的少量材料及文档必须表达的必要事实；必要事实只用于事后比较，不提供给冷读者。冷读材料不自动等于全部直接依赖，不得为阅读便利扩大语义依赖；选定图示可以作为材料，但不得用名单外正文补足图示。

冷读者使用未参与编写、没有前序对话的新上下文，只依角色视图精确引用的正式正文回答入口核心问题，并标记“直接说明、只能推断、没有说明、存在歧义”。导航摘要不具有业务权威性，不得复制正文形成摘要链，也不得用名单外代码、历史、常识或作者补充填空。事实错误、关键遗漏、推断、缺失、歧义或需要名单外材料均不通过。

记录只保存实际材料、一句预期、一句复述、理解断点和结论，不复制完整问答。提交结论后冷读棒次立即闭合并停止。失败后只重读实际修改入口和因此进入后续批准材料的受影响入口。

入口问题围绕当前决策选择：需求是否说清谁遇到什么问题、改后结果与范围边界；验收是否能定位同一场景的实际结果、证据和待判断差异。冷读失败优先修正具体理解断点，不要求补齐所有控件状态或增加媒体。AI 冷读通过不证明人已快速理解，也不替代实际体验或人工批准。

## 最终验收输入合同

既有最终验收角色也承担自动冻结前的独立交付评审，只形成技术与需求符合性建议；主协调者记录真实结论后按冻结规则收尾，不把该建议登记成人工批准。

创建最终验收上下文前，主协调者用 `prepare-handoff --action validation --role final-review --integration-confirmation <文件>` 检查全部候选、独立评审、验证入口和集成确认。缺项回到原材料负责人补齐；准备通过只表示可以交接，不表示业务验收通过，也不授予批准权限。

主协调者给最终验收者的任务消息只交付当前交付项、最终验收角色和集成确认文件定位，不复制正文或验收事实。最终验收者通过 `context-summary --action validation --role final-review` 一次取得已批准需求与验收条件、验证入口、至少一个已接受候选及对应独立评审、集成确认、未验证边界、残留风险和停止条件，不读取实施对话或早期阶段的过程材料。没有已接受实现候选时不形成最终评审角色视图。机器门禁失败时原样返回阻断；机器事实已经完整但任一验收输入仍无法定位或判断时，只返回具体缺项并停止，不自行补全或形成通过结论，也不替用户记录最终业务验收决定。

## 批准与失效

- 需求入口和术语在独立冷读通过、用户明确确认后设为已确认并记录需求批准。需求批准绑定需求入口快照；术语通过需求入口的直接依赖新鲜度进入门禁。
- 重大架构确认绑定设计入口快照，并以前置需求批准仍然有效为条件。
- 最终业务验收绑定验证入口快照，并要求至少一个已接受实现候选；复杂配置同时检查实施收敛门禁，并原子绑定按任务包标识稳定排序的全部已接受候选及独立通过评审集合摘要。最后一个已接受候选按实现执行身份在既有使用顺序中的最后位置确定，最终工作区必须仍与该候选一致，并把同一次检查得到的仓库修订与工作区变化摘要写入批准记录。最终批准必须提交绑定当前候选集合和工作区的集成确认并保存文件摘要，不把该文件当成测试执行证明。实施或验证总览的完成状态不能替代候选。
- 每个已接受候选都必须有结论为通过、执行身份不同于实现身份且候选摘要一致的评审。负向或边界测试证据可以随评审保存，但不是通过结论的格式门槛。封存前候选、评审、集合摘要、集成确认或工作区发生变化时最终批准确定性失效；需要记录新的人工验收时重新确认，普通 DLoop 自动冻结仍按当前交付事实独立核对，DloopUI 必须重新取得有效最终验收。内容未变化时最终验收复用原结果，不因验收、冻结或评审身份机械重跑。最终批准缺少候选集合绑定属于非法合同，直接拒绝读取。
- 候选评审必须复核候选固定的批准方案版本、方案摘要和不可变批准历史引用；当前方案后来升级不能替换历史候选的绑定。
- 默认按绑定入口的正文、语义版本和就绪状态判断批准失效。DloopUI 需求和设计按内部材料就绪检查，最终验收绑定当前交互、证据和已接受候选。需求批准失效会继续使架构、交互和最终批准失效；架构被拒绝或失效会使最终批准失效；封存前最终批准后的工作区变化或新实施修改也会使最终批准失效。封存后批准与验证仅描述当时交付，不因用户后续 debug 重新失效或启动工作流。

阶段模块负责提供和记录各自内容；本模块只定义如何理解、批准、退回及判断旧批准失效。
