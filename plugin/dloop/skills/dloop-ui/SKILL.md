# DloopUI v4.0.0

本 Skill 是 DLoop 的显式 Unity UI 规划配置。它复用同一交付档案、阶段批准入口和实施闭环，提供按需使用的真实 Prefab 定位、随实施更新的场景验收记录与统一验收导航。普通 Unity/UI 请求不得隐式选择本配置。

用户要求暂停或回退时，先停止受影响执行，再读取 `workflow-rules --action slice-release --action snapshot` 中的“人工回退”规则，按同一 DLoop 协调流程处理。

## 固定边界

- 已连接并核对项目绑定的 DLoop MCP 时，开工清单通过 `dloop_prepare_input` 获取模板，再用 `dloop_submit_ui_baseline` 传入对象；不手写 JSON 文件。材料齐备仍须用户确认，只有用途措辞含义不变时才将 `semantic_change` 设为 `false`。其他动作沿用当前 CLI 合同。
- 发现 DLoop 工具或规则需要修复时，在源码中修改并通过新版安装交付；不直接修改项目内已安装载荷或安装锁。已有本地补丁随正常跨版本升级备份保留，不接续旧作业。
- 先提取具有可见表现、用户操作或 UI 去向的需求，再寻找承载需求的现有 Prefab；不得先扫描整个目录并解释所有控件。
- 调查阶段只有经过明确语义判断且当前真实存在的 Prefab 才能截图。不存在、无法唯一匹配、单项截图失败或目标不可见时记录正常跳过，不为补齐截图创建替代资产或占位界面。
- Unity 截图只提供身份、名称、层级和可见矩形；AI 另查本功能相关后端、既有逻辑和界面，核对操作条件与结果。静态截图不能证明运行交互。
- 未被需求明确改变的既有表现全部保留，不逐项枚举按下、回弹、长按或过渡。
- 内部需求整理与最终验收按 DLoop 的业务场景组织；标注条目和 Prefab 不自动成为独立展示场景。截图只证明可见现状，行为沿用依据由相关项目事实核实；规划附件不代替运行验收，不要求前端原型或多状态演示。
- `reuse` 表示产品无需任何修改；接线、刷新状态、改变显示或布局都必须使用 `change`。
- UI 只显示明确状态并发出意图。资格、权限、奖励和业务数据正确性由后端或外部业务模块负责。

## 初始化

先复用用户提供的需求、界面名称、Prefab 或文件夹线索，在当前项目内寻找承载需求的资产；不要求用户先找全文件。缺项目位置或访问能力时只补问该缺项；已能查找时先调查，再集中说明找不到或无法唯一匹配的界面、依据与影响。调查可以直接进行；实施前须提交四类材料清单并取得用户对当前清单的明确确认。

未提供 Prefab 或搜索无结果不构成创建授权。必需的预制体、协议、配置或需求描述缺失、有歧义时，停止整个需求的实施；不能用计划新增、占位、延期或正常截图跳过替代开工条件。用户明确要求制作缺失资源时，先由用户决定单独准备资源或拆出独立范围，不能自行缩减原需求。调研保留 `not-found` 或 `ambiguous`，不把建议路径登记为真实匹配。

先查项目内已有材料，再集中说明缺什么、查过哪里、影响什么功能以及需要用户补充什么。缺项期间仅继续读取、调查和保存资料，不修改业务代码、预制体或业务配置，也不推测缺失业务事实编造设计。用户补齐后复查受影响内容；补齐不等于批准开工。

用当前需求材料初始化同一 DLoop 交付项；来源参数可以重复。来源须是已存在的本地 UTF-8 材料；网页先读取正文并保存带原链接和定位的本地摘录，再登记该文件。不要把 URL 传入本地路径参数。已有档案的初始化不会替换来源。

~~~powershell
python Tools/FeatureArchive/feature_archive.py init `
  --feature-id <stable-feature-id> `
  --title <中文功能标题> `
  --configuration dloop-ui-v1 `
  --source-document <需求文件或已有-DLoop-资料>
~~~

初始化只登记来源。`ui-model.json` 是 module 生成的内部事实，不直接编辑；计划和 SVG 也不直接编辑。

内部 UI 模型和正式截图按证据与候选绑定核对，不填入产品写入范围。临时采集使用工具返回的本版本 `captures/<feature-id>/` 位置；不自行选用其他临时目录。产品预制体及生成代码仍须逐项授权。

初始化后或继续已有 UI 交付时，先读取 `workflow-rules --action snapshot` 的完整规则，按其要求处理阶段起点、覆盖旧材料、提交评审、阶段完成和中断恢复。保存失败时先恢复，成功前不得继续编辑或交接。

## 界面调研

本轮首次进入调查阶段时，在编写调研简报和调用调查命令前保存阶段输入：

~~~powershell
python Tools/FeatureArchive/feature_archive.py snapshot-save `
  --feature-id <stable-feature-id> --reason stage-start --stage investigation
~~~

同一轮次不重复标记阶段开始；阶段重做成功后，新一轮重新保存起点。

读取全部已登记来源，为每条 UI 需求形成一份完整的 `ui-brief.json`：

- 业务键、名称、可观察描述、来源路径和精确定位；
- 页面名、文案或功能名等定位线索；
- 明确需求或合理推断，以及 high/medium 置信度；
- `matched`、`not-found` 或 `ambiguous` 匹配结论。

提取后回到原始段落或图片核对操作去向、显示对象和结果范围，不能只审查已经提取的条目。不同信息对象、展示位置与排序含义必须区分；时间到达等会改变页面的触发也属于需求，不因截图只能显示静态状态而遗漏。复用组件不能改变需求规定的操作去向；缺字段、缺页签或目标不可见仍保留原需求，交由常规计划明确承接和恢复条件，不能以正常跳过缩减业务范围。

同一行为涉及多个位置或触发时，分别说清条件、操作和结果。隐藏画面与可见切换入口不能合并后整项跳过。复用本功能必需的入口也保留说明，不普查全项目，不机械穷举控件状态。

`matched` 只提交项目 `Assets` 下的真实 `.prefab`；`ambiguous` 至少列出两个真实候选。详细字段见 [业务输入合同](references/model-contract.md#界面调研简报)。

~~~powershell
python Tools/FeatureArchive/feature_archive.py ui-investigate `
  --feature-id <stable-feature-id> `
  --input <ui-brief.json>
~~~

默认返回 `awaiting_capture` 和 `capture_request` 时，保持项目打开，通过 Unity MCP 在该项目调用已有截图器；具体调用见 [当前编辑器采集](references/model-contract.md#当前编辑器采集)。请求只是临时材料，正式模型和已有计划保持原样；此时尚不能发布新标注或称为调研完成。采集后按返回的下一动作提交清单：

~~~powershell
python Tools/FeatureArchive/feature_archive.py ui-investigate `
  --feature-id <stable-feature-id> `
  --input <同一份-ui-brief.json> `
  --capture-manifest <当前编辑器生成的-capture-manifest.json>
~~~

命令仍核对实际资产身份、摘要、截图与区域，成功后统一导入和维护内部证据。不要手改模型或用临时脚本替换工具内部适配。没有已匹配 Prefab 时不需要 Unity，直接取得前置跳过结果。只有明确选择批处理且项目未在其他编辑器打开时才传 `--unity-executable <Unity.exe>`；环境变量不会自动选择批处理。MCP 不可用时说明实际缺少的采集能力，不要求用户关闭工作项目来尝试批处理。

结果为 `ready_for_review` 时，读取返回的原始截图和区域；`ready_to_publish` 表示全部需求已经形成前置跳过，可以直接提交空评审。Unity 整体不可用时停止并修正环境，不伪造成单个 Prefab 的业务跳过。

## 开工材料核对与确认

调查后按 [开工清单合同](references/model-contract.md#开工清单) 核对每项需求的预制体、协议、配置和需求描述。每份已登记来源必须形成需求，或显式列入“本次明确不做”；不得只处理容易实现的段落。尽早提交已知缺项；全部齐备、设计和计划形成后，在首次实施之前统一展示一次。沿用已有协议或配置时引用真实提供能力的文件，不能写成“不涉及”；确实没有该类依赖时才说明理由。预制体与需求描述不可省略。文件存在不等于业务事实齐全，必须核对节点、字段含义、触发条件、结果和关键异常。

1. `prepare-action-input --feature-id <id> --input-kind ui-baseline` 取得完整输入合同，填写后按返回动作提交。
2. `ui-baseline --feature-id <id> --input <清单路径>` 保存缺项并返回集中清单，或返回当前确认材料和摘要。先按下一动作补齐内部文档，再展示开工确认；材料 `ready` 不代表内部文档已齐备。缺项按业务结果集中说明已查位置、缺少的事实及影响；没有新证据或业务决定时不重交，也不只换措辞反复提交。
3. 首次齐备或业务依据变化后，读取并向用户展示返回的确认材料，逐业务场景说明预期结果、预制体、协议、配置与需求依据。等待用户真实回复；再用 `stage-action --stage ui-baseline` 携带当次摘要、决定及用户回复定位和原文记录确认。AI 评审、资料补充、沉默和以前的泛化“继续”不代替本次确认。

使用材料或业务范围改变时，暂停实施并更新清单，重新展示变化后取得确认；不得沿用旧回复。仅修正清单用途措辞且含义不变时，以 `ui-baseline --semantic-change false` 重交；返回 `approval_preserved: true` 时按下一动作继续，不重复索取确认。仅补截图、内部标注或不改变业务含义的实现调整无需重新确认。启动、恢复、返修和实施交接统一检查当前确认，缺项不能由 AI 自行拆分后绕过。

## 更新内部交互草稿

本轮首次进入计划阶段时，在编写标注评审和发布标注前保存已经取得的调查结果：

~~~powershell
python Tools/FeatureArchive/feature_archive.py snapshot-save `
  --feature-id <stable-feature-id> --reason stage-start --stage plan
~~~

同一轮次不重复标记开始；重做后按新一轮保存，覆盖旧成果前仍按快照规则保留现场。

根据调研结果形成完整的 `ui-review.json`，必须携带当次 `investigation_token`。每个未在调研阶段跳过的需求都要形成：

- `change`：选择截图区域或截图内矩形，并说明本次修改和用户可观察结果；
- `reuse`：选择截图区域，只确认现状已经满足需求，不填写实施动作；
- `target-not-visible`：只能基于成功截图，说明为什么无法可靠定位目标。

详细字段见 [业务输入合同](references/model-contract.md#界面标注评审)。

~~~powershell
python Tools/FeatureArchive/feature_archive.py ui-publish `
  --feature-id <stable-feature-id> `
  --input <ui-review.json>
~~~

发布会一次完成模型保存、机器检查、旧结果清理、统一 HTML、编号 SVG 和归档表格生成。相同输入可重复执行；重新调研会撤销旧匹配、截图标注、跳过和不再生成的媒体。过期 token 必须重新查看最新截图，不能继续使用旧评审。

初期可发布不完整内部草稿；截图和标注的完整性不代替四类材料核对。正式实施仍须通过开工确认。不要把内部材料状态 `confirmed` 或 `ready` 当作用户批准。每完成一个功能单元，核对相关后端字段、既有代码与实际界面；字段存在本身不能证明需要增加产品交互。

## 尽早验证真实入口

调查时就核对测试账号、服务端或外部数据、功能开放状态、进入路径和准备责任人，将缺项与可完成的客户端验证边界纳入开工说明。协议文件存在不代表环境已有可用数据。

实施启动后用 `prepare-action-input --input-kind acceptance --execution-id <执行身份>` 生成场景记录，先填写准备条件、入口和最短操作。先完成“打开真实入口、看到非空业务数据、正常退出、重新进入或刷新后状态正确”的最小运行冒烟，再铺开后续交互；该结果写入同一验收文件，不增加独立审批或状态机。无法运行时立即保持 `unverified`、记录具体缺项并尽早请用户协助，继续已授权且不依赖该环境的工作，不等到交付末尾才询问环境。

同一份场景记录随实施更新：`static` 仅表示静态检查，`isolated` 表示受控数据下的客户端隔离验证，`runtime` 表示真实产品环境中的实际操作；不得把前两种写成实际验收通过。必要真实验证未完成仍保留未验证；用户明确延期时记录依据，不自行降低要求。

## 实施中补全

使用项目绑定、配置或协议生成器前，运行其已有只读预检查，将预计写入路径填入任务包 `generated_write_scope`。绑定生成包括目标预制体、绑定脚本、缺失时才创建的逻辑和新增元文件；配置与协议生成包括代码及数据输出，不能只登记源表或手写代码。工具在登记和启动前核对这些路径全部属于授权范围。生成目标或配置改变时重新核对预计写入，超出当前范围先交还协调者。

- 原范围内有明确依据的遗漏，补齐实现并更新受影响的同一份场景记录。必要的任务范围调整先交还协调者按原管理流程处理，不越界后追认。
- 缺少必要业务事实、存在冲突、必须由用户选择或需要扩大授权时，暂停整个需求的实施，把缺项或歧义登记到开工清单并集中提出具体问题及影响；用户明确拆分独立范围后才按新范围核对和确认。
- 场景内保留本次变化、关键异常和时间/推送触发的结果。常规返回、沿用控件和未改动的通用弹窗不重复写说明；实现核对仍覆盖完整原需求。
- 无法截图定位不妨碍交回场景验证；只有选择提交局部标注时才填写真实节点或 `target.unavailable_reason`，不为交付材料补造截图。
- 候选评审从原始需求查实现，再从实际实现查场景验收记录；不能只审核已抽取条目。协调者在最终候选接受后完成整体双向核对。

先通过 `prepare-action-input --input-kind task-package` 取得任务包合同。每个业务验收场景在 `delivery_requirements` 中默认只声明 `acceptance` 场景验收记录。多个功能点共享一个场景及其证据，不按控件或 Prefab 拆分材料要求；仅有位置争议、视觉变化或难复现状态时追加截图、节点定位或局部交互说明。此处是候选交付证据清单，非必要证据写明范围或延期依据；不能用证据延期绕过开工所需的业务材料及用户确认。

实施者使用 `prepare-action-input --input-kind candidate --execution-id <执行身份>` 取得本任务材料清单，通过 `delivery_materials` 交回文件路径和内容定位。交互与元素定位可引用同一份本任务交互 JSON；截图必须引用当前调研登记的原图，验证材料如实填状态。实施中发现同一验收场景的材料遗漏，随候选追加 `additional_delivery_requirements`；不能通过追加材料扩展业务范围或撤销原要求。文件和定位缺项由提交入口逐项报告，补齐后用原执行身份重交；不以对话中的完成声明代替交接。完整字段见 [材料交接合同](references/model-contract.md#任务材料交接)。

## 最终统一展示与验收

HTML 默认只回答：改了什么、去哪里验收、实际验证了什么、还差什么。按业务场景展示变化、入口、准备条件、验证层级及结果、待完成事项；简短操作与证据默认折叠。已有截图和逐控件定位作为可选附件，不占据默认验收页面，不为填满模板重述需求或制作第二套 UI。

实施者交回的 `acceptance` 文件同时供评审和展示使用。候选接受后通过 `prepare-action-input --input-kind ui-delivery` 取得最终输入，协调者只补整体需求与实现核对结论；工具从已接受候选汇总场景记录。记录内容只写一次，不再填写逐控件 `outcomes`。合同见 [场景验收记录](references/model-contract.md#场景验收记录)。

统一使用 `ui-publish` 和 `06-validation/ui-delivery.html`。已接受候选中必要验证未完成时，也可以生成当前成果页，但 `delivery_ready` 为 false，最终批准和冻结仍被阻断。候选尚未接受时沿用现有内部草稿；不另写人工 HTML，不把草稿或静态检查说成最终通过。

材料变化时只在最终输入的 `material_updates` 替换受影响引用；同一文件服务多个场景时，一并更新相关引用。行为错误仍走实施返修和独立评审，不能用改报告代替修产品。验收记录和其证据均绑定当前候选；修改后需重新核对。

后置验收仅在视觉变化、位置争议或难以复现的状态需要额外截图。布局或节点改变时补拍受影响页面；纯逻辑或文案变化且位置未变时，按调研合同复用已有定位，不重新全量采集。静态预制体截图只证明位置，实际行为使用运行记录或录像。选择使用标注时，元素路径和核对依据默认收起；同一功能点的多个操作共享编号。

交付页在真实浏览器中检查默认与窄窗口：场景是否可扫描、证据链接是否可用、展开步骤与可选定位是否正常。不要求为每个业务需求测试 HTML 控件。采集和浏览器控制完成后释放控制上下文。

用户可以直接在游戏或产品中完成验收。记录实际验收场景、结论及未完成项后，用 `workflow-status` 返回的当前摘要通过 `stage-action --stage final` 登记同一次用户回复及集成确认；不再要求用户重复确认 HTML 中的同义描述。未收到回复不能自动批准或封存。
